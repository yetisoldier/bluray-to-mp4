**Status:** design
**Author:** Bob (architect)
**Implements:**
(A) finalize-phase heartbeat — distinct monitor step labels for concat, frame-count
    gate, and clock gate, plus a periodic state refresh so `update_age` stays fresh
    during the long mezzanine decode gate, and a health-model rule that
    distinguishes heartbeat-alive finalize silence from a true hang;
(B) per-chunk resume — a re-entered `run_dvd_upscale` verifies and reuses existing
    `chunk_NNNN/segment.mkv` files instead of recomputing all N chunks;
(C) Karen's five v0.2.34 patch-forward findings (dead import, CFR fail-open gap,
    snap-band cross-provenance guard, success-path diagnostic parity, doc
    correction);
(D) version surface (scope addition from Eric, field-debugging driven): the app
    version is visible in the UI, exposed in the monitor payloads, and recorded
    per History row — one `__version__` source of truth, no hardcoded copies.
**Fixes:** the 2026-10-19 Mamma Mia HWA v0.2.34 field run: after chunk 57/57
completed at 12:58, the monitor sat at `progress=1.0 / step='chunk complete'`
with **no update for ~65 minutes** while the app legitimately ran concat +
`verify_mezzanine_frames` (full FFV1 decode count of 163,509 frames) +
`verify_mezzanine_clock`. The app's own `classify_snapshot` self-reported
`stuck` (`stale_seconds=300`) during legitimate work; the operator's run watcher
false-fired STALL five times; the run was nearly killed, which would have cost
~5 GPU-hours because there is **no per-chunk resume** — an interrupted
`run_dvd_upscale` restarts all 57 chunks from zero.

Repo state at design time: `main` @ e62a80e (v0.2.34, released and
field-validated same day). Suite baseline: 334 passed (venv) / 288+1 skip
(system). Line numbers below are from e62a80e.

Constraints honored: no keyframe-seek scope, no model/packaging changes, no

## 1. Current mechanism at the finalize boundary (verified, e62a80e)

- The chunk loop in `run_dvd_upscale` (`upscale.py:536-699`) calls
  `report(frac, step, idx)` per sub-step (steps at 562/640/666/699); after
  the final chunk, `len(segments)/chunks == 1.0` is reported with
  `step="chunk complete"` (699).
- **Then silence.** The concat block (`upscale.py:701-728`: concat-demuxer
  `-c copy`, or the single-chunk `shutil.move`), the "mezzanine not created"
  size check, `shutil.rmtree(workroot)` (732), and `return` emit **no progress
  callbacks at all**. Back in the pipeline, `verify_mezzanine_frames`
  (`pipeline.py:991-994`, a full `-count_frames` decode of the FFV1
  mezzanine — observed 20-60 min on a 113-minute title) and
  `verify_mezzanine_clock` (`pipeline.py:1002-1005`, cheap) also emit
  nothing.
- Monitor plumbing: `workers.py:152-167` maps every upscale progress tuple to
  `monitor_state.update(progress=frac, ..., step=...)`. `MonitorState.update`
  (`monitor.py:203-236`) refreshes `updated_at` on **every** call, but
  `progress_updated_at` only when progress changes by ≥ 1e-4. During
  finalize, neither moves.
- Health model: `classify_snapshot` (`monitor.py:44-103`) fires
  `"stuck"` when `update_age >= stale_seconds (300)` **or** when
  `progress_age >= stale_seconds` with `progress >= 0.999`. During a legit
  65-minute decode gate, **both** trip. Current exceptions: only an
  initial-upscale grace (`stage` starts with "upscaling" && progress ≤ 0.001
  gets 1800 s — `UPSCALE_INITIAL_STALE_SECONDS`). No finalize-phase
  awareness exists.
- UI label ownership (6ca6216 single-writer lesson): the Encode card's
  `time_remaining` is owned solely by `_forecast_total`
  (`ui/main_window.py:1315-1337`); per-stage ETA lives only on
  `stage_bar.eta_label`; the chunk/step line is written solely by
  `_run_progress` (`main_window.py:1390-1394`,
  `progress_stage.setText(f"Upscaling: chunk {c} of {n} - {step}")`).
  `on_stage` text is a *different* writer (`_run_stage`,
  `main_window.py:1360-1384`) and must not be used for finalize
  sub-labels, or the two writers will fight over `progress_stage`.

## 2. Feature A — finalize-phase heartbeat

### 2.1 Step labels (what the operator sees)

Inside `run_dvd_upscale`, the existing `report()` closure gains three
finalize-phase emissions; no new plumbing — the same
`("upscale", tid, frac, eta, detail)` tuple, the same `detail.step` field the
UI already formats:

| Point | `detail.step` | `frac` |
|---|---|---|
| concat/multisegment move start | `"concatenating mezzanine"` | clamped (§2.2) |
| before pipeline's `verify_mezzanine_frames` | `"verifying frame count (full decode)"` | clamped |
| before pipeline's `verify_mezzanine_clock` | `"verifying audio clock"` | clamped |

The first is emitted from `run_dvd_upscale` itself (it owns concat). The
second and third are emitted from the **pipeline** call site
(`pipeline.py:991-1005`), immediately before each gate call, reusing the
same `on_progress` lambda the stage already passes to `run_dvd_upscale`
(`pipeline.py:973-977`) with `detail={"chunk": chunks, "chunks": chunks,
"step": ...}` — the UI line then reads
`Upscaling: chunk 57 of 57 - verifying frame count (full decode)`, which is
honest: the chunk *count* is done, the *finalize* step is named, and the
operator sees exactly WHERE the run is.

**ffprobe emits no progress** during `-count_frames`; the honest fix is the
step label + the heartbeat (below). **No fake percentages**: `frac` does not
advance during a decode gate; only `step` and the freshness timestamps move.

### 2.2 Frac clamp during finalize

The CLI (`cli.py:225-237`) prints a **newline** when `frac >= 1.0`; a
periodic heartbeat at exactly 1.0 would emit one line per tick for the whole
decode window. Finalize-phase reports therefore clamp:
`report(min(0.999, frac), step, last_idx)` — the bar sits at 99.9% with a
named step, which is the *true* state (the mezzanine is not yet proven).
Chunk-loop reports are untouched.

### 2.3 Heartbeat thread (what keeps update_age fresh)

Step transitions alone are three calls minutes apart — a 20-60-minute decode
gate between "verifying frame count" and "verifying clock" still exceeds the
300 s stale window. New helper in `upscale.py`:

```
class _ProgressHeartbeat:
    """Pings on_progress every `interval` seconds with the last
    (frac_at_start, step, idx) until stop(). Daemon thread; never raises."""
    def __init__(self, on_progress, *, interval: float = 15.0): ...
    def start(self, frac: float, step: str, idx: int, chunks: int) -> None: ...
    def stop(self) -> None: ...
```

Mechanics:

- Interval **15 s**: 12× inside the 300 s stale window with headroom for
  scheduler jitter; negligible log/UI cost. Fixed module constant
  `_FINALIZE_HEARTBEAT_SECONDS = 15.0`, no config surface (constraint).
- Each tick calls `on_progress(0.999, None, {"chunk": chunks,
  "chunks": chunks, "step": current_step, "heartbeat": True})`. The
  `"heartbeat": True` key lets consumers distinguish a liveness ping from a
  real state change; the monitor update path ignores it (same fields),
  refreshes `updated_at`, and — because clamped frac and `step` may be
  unchanged — does **not** move `progress_updated_at` (progress genuinely
  did not move; that timestamp keeps meaning what it means).
- **Placement — two scopes:**
  1. `run_dvd_upscale`: a heartbeat wraps the concat/move block and the
     final size-check + workroot cleanup (seconds to ~1-2 min; cheap
     insurance; `shutil.move` of a multi-GB single-chunk segment across
     filesystems can itself take minutes).
  2. Pipeline gate block (`pipeline.py:991-1005`): a heartbeat wraps the
     two `verify_mezzanine_*` calls. The pipeline does not own a `report`
     closure, so it constructs `detail` directly and calls the same
     `on_progress` lambda; the heartbeat helper lives in `upscale.py` and is
     imported, or (simpler) the pipeline instantiates
     `_ProgressHeartbeat(on_progress)` — name it public
     (`ProgressHeartbeat`, exported in `upscale.__all__`) since two modules
     share it.
- **Single-writer discipline (6ca6216):** the heartbeat writes only through
  the existing `on_progress` path. No `on_stage` calls for finalize
  sub-labels (that would hand `progress_stage` to a second writer and
  re-introduce the flicker class). ETA stays `None`: `_forecast_total`
  continues to own `time_remaining`, and with `_stage_now == "upscale"` and
  `_stage_eta is None` the forecast already includes the fallback
  `upscale_seconds(d)` — the finalize heartbeat changes no forecast
  arithmetic (it must NOT set `_stage_eta`, or the card would flash a
  bogus estimate; asserted by test U-A3 below).
- `EncodeCancelled` responsiveness: heartbeat is a daemon thread; cancel
  handling is unchanged (the ffprobe/ffconcat processes are polled by
  `_run_process`'s cancel loop as today).

### 2.4 Health model: legit-silence vs hang

`classify_snapshot` (`monitor.py:44-103`) gains **finalize-awareness** so the
app stops self-reporting `stuck` during heartbeat-alive finalize, while a
true hang (heartbeat dead = `updated_at` stale) still fires:

```
FINALIZE_STEPS = frozenset({
    "concatenating mezzanine",
    "verifying frame count (full decode)",
    "verifying audio clock",
})
```

Rule change inside the `busy` branch:

- If `snapshot.step in FINALIZE_STEPS` (string compare against the exact
  tokens above) **and** `update_age < stale_seconds` (the heartbeat is
  alive), then the `progress_age >= stale_seconds and progress >= 0.999`
  reason is **suppressed**. Rationale: during finalize, frozen progress at
  the clamp value with a fresh `updated_at` is the *designed* state; the
  freshness check has already been delegated to the heartbeat cadence
  (15 s ≪ 300 s), so `update_age` is the honest liveness signal.
- If `update_age >= stale_seconds`, the existing `"no monitor update"` stuck
  fires unchanged — heartbeat dead **is** the hang signal. This is the
  external-watcher contract: Jarvis/Eric's watcher reads
  `health.status`; a heartbeat-alive finalize reads `running` with
  `update_age_seconds < 15`, a wedged ffprobe reads `stuck` with
  `update_age_seconds >= 300` and the reason string. The 2026-10-19
  five-false-STALL shape cannot recur: legit silence is *expressed* (step
  names the phase; update_age proves the heartbeat).
- `stale_seconds` (300) and `UPSCALE_INITIAL_STALE_SECONDS` (1800) are
  unchanged. No new config knobs (constraint).

Snapshot needs `"step"` in the payload — already present
(`monitor.py:279`). `classify_snapshot` reads `snapshot.get("step")`; no
schema change.

## 3. Feature B — per-chunk resume

### 3.1 The observed cost model

`run_dvd_upscale` today: unlinks its output mezzanine at start
(`upscale.py:531-535`), `shutil.rmtree`s each chunk's `in`/`out` dirs at
chunk start (`upscale.py:552-553`, and again at end-of-chunk 697-698),
rmtree's the **whole workroot on success** (`upscale.py:732`), and —
importantly — on exception it unlinks only the partial *output*
(`upscale.py:738-742`) and **leaves the workroot
on disk**. So the resume material (per-chunk `segment.mkv` files) already
survives interruption; nothing currently *uses* it.

### 3.2 Resume unit = verified `chunk_NNNN/segment.mkv`

PNG dirs are **never** resume units: an interruption can land after all
upscaled PNGs but before segment mux, making a partial `out/` indistinguishable
from a complete one without deep inspection. Only a complete, verified
`segment.mkv` earns reuse; `in/` and `out/` are always recomputed for a chunk
that is being recomputed. Strict + cheap, and it bounds the verification
surface to exactly one file per chunk.

### 3.3 Resume precondition: plan fingerprint

A segment computed under a different plan must never be reused. At attempt
start, `run_dvd_upscale` writes `workroot/resume_manifest.json`:

```json
{
  "version": 1,
  "input_path": "<abs plan.input_path>",
  "mode": "720p",
  "binary_sha_basename": {"binary": "<resolved realesrgan path>",
                          "model": "<model_name_for_mode>"},
  "fps": "24000/1001",
  "total_frames": 163509,
  "chunk_frames": 2877,
  "deinterlace": false,
  "target_height": 720,
  "segment_filter": "scale=-2:720:flags=lanczos,setsar=1",
  "esrgan_scale": 2
}
```

Fingerprint comparison is **whole-file equality** of the JSON (sorted keys)
except an informational `"attempt_started_at"` field excluded from the
comparison. Mismatch (or unreadable/corrupt manifest) → the workroot is old
garbage from a different intent: `shutil.rmtree(workroot)` and start fresh —
failing closed, same philosophy as the v0.2.12 rip-reuse width tier
(`pipeline.py:735-748`). `chunk_seconds` is **not** in the fingerprint
directly; `chunk_frames` + `total_frames` fully determine the bounds math,
which is what must match.

### 3.4 Per-chunk decision inside the loop

At each `idx`, before touching `in/`/`out/` (replacing the unconditional
rmtree at `upscale.py:552-553`):

```
segment = chunk / "segment.mkv"
if segment.is_file() and _verify_segment(segment, count, plan.fps, ffmpeg_probe):
    segments.append(segment)
    report(len(segments) / chunks, "resumed chunk", idx)
    continue                       # in/out dirs never created
shutil.rmtree(in_dir, ...); shutil.rmtree(out_dir, ...)   # as today
... extract + upscale + mux as today ...
```

`_verify_segment` — cheap and strict, in `upscale.py`:

1. **Decodability + count, one probe:**
   `ffprobe -v error -select_streams v:0 -count_frames
   -show_entries stream=nb_read_frames,r_frame_rate -of json segment.mkv`.
   FFV1 decodes >1000 fps; a 2877-frame segment costs ~2-3 s; a 57-segment
   full-resume verification costs ~2-3 min **once**, vs ~5 GPU-hours
   recomputed. No metadata fast path: `nb_frames` *metadata* is the exact
   lie class §2.1 of the v0.2.33 design retired for the rip; the segment
   file is ours, but the strict rule is uniform and the cost is bounded.
   Any ffprobe failure / missing fields → not resumable (recompute).
2. `int(nb_read_frames) == count` (this chunk's expected count from
   `bounds[idx]` — includes the remainder chunk's 2397, not F).
3. `r_frame_rate == plan.fps` — compared after token normalization
   (`parse_frame_rate`-style: both sides through the existing
   `parse_frame_rate` in `ffprobe.py:97-110`; string-equal on the canonical
   token). A segment stamped at a different clock is re-muxed via recompute
   (the count gate alone is blind to the v0.2.34 lie class).
4. Size sanity: `segment.stat().st_size > 0` (guards the sparse/zero-byte
   edge an interrupted mux can leave with a plausible header).

All four pass → reuse. Anything else → recompute *that chunk only*.
Per-chunk PNG-count assertions on **newly computed** chunks are unchanged
(`upscale.py:611-624, 655-673`); resumed chunks skip them by construction
(their truth was proven at segment verify; re-reading PNG dirs from a prior
attempt is explicitly out of scope per §3.2).

### 3.5 Interaction with the output-mezzanine unlink

A prior attempt interrupted *during concat* leaves a truncated/stale
`plan.output_path` (the pre-concat unlink at `upscale.py:531-535` already
deletes any previous mezzanine at entry). **Concat is redone every attempt**
(cheap: demuxer + `-c copy`, minutes), so resume semantics end at the
segment layer — the unlink stays, the finalized mezzanine is always rebuilt
from (reused or recomputed) segments, then re-gated. No change needed beyond
keeping the existing unlink where it is.

### 3.6 Interaction with the pipeline-level `.rip` purge

`pipeline.py:686-700` (the `_expected` set is built at 688) purges every entry in `rip_dir` not equal to a planned
`job.input_path` before ripping. The upscale workroot lives at
`rip_dir/.upscale/title_{tid:02d}_work/` and the mezzanine at
`rip_dir/.upscale/title_{tid:02d}_720p.mkv` — **currently both purge
targets**, which would destroy the resume material at re-entry. Spec:

- `_expected` gains, per job with `upscale_mode != "off"`,
  `os.path.normcase(os.path.join(rip_dir, ".upscale"))` — preserving the
  whole `.upscale` tree (workroots + any finished mezzanines) exactly as the
  rip-reuse lane preserves complete rips. The anti-hang guarantee is
  unaffected: the purge exists for `makemkvcon`'s interactive overwrite
  prompt, which only concerns top-level rip outputs; `.upscale/` is never a
  makemkv target.
- **The rip itself must NOT be purged by anything in this feature** — stated
  explicitly for the regression suite: the v0.2.12 duration+width reuse lane
  (`pipeline.py:712-770`) is untouched and runs first; if it rejects the rip
  (different master, partial), the rip is re-ripped and the *upscale*
  fingerprint (input_path identical, but the manifest records it) — note:
  a re-rip yields the same path but potentially different decode truth. The
  pre-flight runs before `run_dvd_upscale` every attempt
  (`pipeline.py:875-949`): `total_frames`/`fps` in the manifest are compared
  against the CURRENT attempt's freshly derived values, so a re-ripped file
  with a different frame count or clock invalidates the fingerprint → full
  recompute. Honest by construction.
- **Success-path reclamation:** unchanged — `run_dvd_upscale`'s
  `shutil.rmtree(workroot)` on success (`upscale.py:729`) still removes the
  workroot after a completed mezzanine (the resume value is spent by then),
  and the end-of-run `.rip` reclaim (`pipeline.py:1102-1118`) is unchanged
  (full success + default workdir, retention-suppress honored).
  *(v0.2.36 correction, found in Karen's review of the shipped code: the
  success rmtree runs INSIDE `run_dvd_upscale`, which returns before the
  pipeline's frames/clock gates — so on a gate trip the workroot is
  already gone and the next attempt recomputes from a clean tree; only
  an INTERRUPTION mid-stage leaves the workroot for resume, which is
  the resume path that actually matters. The manifest check still runs
  every attempt and clears mismatched leftovers.)*

### 3.7 UI/monitor surfacing of resume

- The resume decisions surface through the existing step channel:
  `detail.step = "resumed chunk"` (§3.4) makes the UI read
  `Upscaling: chunk 12 of 57 - resumed chunk` while burning through verified
  segments at seconds-per-chunk — visually distinct from `"AI upscaling"`.
- One stage line at loop start summarizing the split:
  `on_stage` is NOT used (single-writer discipline — `_run_stage` owns
  `progress_stage`); instead the first loop report carries the information
  in step text: chunks up to the first recomputed chunk report
  `"resumed chunk"`, so the operator sees the resume ratio directly in the
  chunk counter (chunk 34 of 57 reached in 2 minutes = 33 resumed). For the
  log/debug lane, a single `_debug_line` per attempt:
  `resume: reused=33 recompute=24 fingerprint=match`.
- Monitor: no new fields; `step` carries it (already in snapshot).

### 3.8 Multi-title/series interaction

Per-job workroots are `title_{tid:02d}_work` — resume is per-title, matching
the per-job isolation already in the pipeline. A cancelled run mid-title-3
resumes title 3's chunks; titles 4+ start fresh. No cross-title semantics,
matching the current fail-open-per-job model (C6).

## 4. Feature C — Karen's patch-forward findings

All five are Low/Info; all are fixed here. (1), (2), (4) are surgical;
(3) is the one real design item; (5) is doc-only.

### C.1 Dead `video_frame_rate` import — remove

`pipeline.py:47` imports `video_frame_rate`; grep-verified dead since
v0.2.34 replaced the metadata read with the derived rate (the only other
references are `ffprobe.py` itself and `tests/test_pipeline.py:24,193-208`,
which import it directly from `ffprobe` — unaffected). Remove the name from
the `from .ffprobe import (...)` list in `pipeline.py:34-50`. The helper
stays in `ffprobe.py` (v0.2.34 §1.4: "not deleted and not rerouted").

### C.2 CFR-check fail-open gap — wrap raw probe crashes into UpscaleError

At `pipeline.py:905`, `cfr = probe_cfr_check(job.input_path)` runs inside
the inner `try` whose handler (`pipeline.py:1007`) catches **only
`UpscaleError`**. `probe_frame_count` and `probe_audio_duration_seconds` are
each wrapped `except FfprobeError → raise UpscaleError` (897-903, 925-931);
`probe_cfr_check` is not. A raw ffprobe crash inside it (binary missing,
OSError, nonzero exit, malformed JSON — all surface as `FfprobeError` from
`_run_ffprobe_json`) escapes the inner try and is caught by the **per-job**
`except Exception` at `pipeline.py:1096-1100`: the whole job is marked
failed despite a healthy encodeable rip — fail-open semantics broken for
exactly the tool-failure class the fail-open exists for.

Spec: wrap identically to its siblings:

```
try:
    cfr = probe_cfr_check(job.input_path)
except FfprobeError as exc:
    raise UpscaleError(
        f"CFR pre-flight could not probe the rip ({exc}); refusing "
        "to upscale a rip whose clock cannot be verified"
    ) from exc
```

The refusal text is distinct from the VFR/UNKNOWN verdict text (the tool
failed, not the rip) so diagnostics/logs tell them apart. Same handler →
fail-open encode of the original rip: CFR-check tool failure now fails
**OPEN**, matching the other two probes.

### C.3 Snap-band cross-provenance guard (design item)

**The blind spot, concretely.** v0.2.34 §1.2 snaps
`rip_total_frames / audio_stream_extent` to a canonical rate within 0.1%.
The neighbor separation is 4.3% (24000/1001 vs 24) — but that gap is *not*
protection when the **denominator is mis-measured into the gap**. A true
23.976 film whose audio stream extent under-reports by 3-12 s (container
lead-out trimming, stream handoff padding — the same skew class §3 of
v0.2.34 tolerates at the clock gate) inflates the derived rate:

```
163509 / 6818.4 = 23.9775  -> snaps 24000/1001   (correct)
163509 / 6807.0 = 24.0206  -> snaps 24/1         (audio -11.4 s; 0.086% from 24)
```

At the wrong snap, the mezzanine plays for `163509/24 = 6812.9 s`; the clock
gate compares against the *same* under-reported audio extent (6807.0 s) —
delta 5.9 s, tolerance max(2.0, 6.8) = 6.8 s — **passes**. Co-moving
operands: both the snap input and the gate reference derive from the same
flawed figure, so neither the snap tolerance nor the clock gate can see the
error. The shipped MP4 then drifts ~0.18% (23.976 vs 24) — audible over a
film-length play as a slow sync walk; exactly the class v0.2.34 exists to
kill.

**The guard: an independent second derivation.** The container **format
duration** (`format=duration`, `probe_duration_seconds`, ffprobe.py:151-179)
is an independent provenance from the audio *stream* extent: it is the
muxer's container-level extent, not the stream's self-report. v0.2.34 §1.1
already *probes* it (the 25%-skew sanity) but only uses it as a refusal
oracle at coarse tolerance. v0.2.35 promotes it to a cross-provenance rate
check at snap time:

```
format_seconds = probe_duration_seconds(rip)              # already available
format_rate    = rip_total_frames / format_seconds        # second opinion
a_tok, _       = snap_to_canonical_rate(derived)          # existing decision
f_tok, _       = snap_to_canonical_rate(format_rate)      # may raise -> below
snaps_agree    = (a_tok == f_tok)
```

Failure behavior:

- **Within-band agreement (both snap to the same token):** proceed silently
  (diagnostic records both figures; C.4). Today's disc: format duration
  ~6819.8 → format_rate 23.975 → both paths snap 24000/1001.
- **Neighbor split (the two snap to DIFFERENT canonical tokens — the blind
  spot firing):** **refuse** before GPU work. The two independent clock
  derivations disagree about the rate class; picking either would be the
  guess v0.2.34 §1.3 forbids. `UpscaleError` names both rates, both snap
  tokens, both durations (stream extent vs format), and the delta that
  would silently decide it — fail-open encode of the original rip, honest
  warning. Refusal, not warn: a neighbor split is *measurable disagreement
  between two truths*, and the cost of refusing (ship original rip) is
  dwarfed by the cost of shipping a 0.18% desync that no downstream gate
  can catch.
- **Format-side unsnappable, audio-side snapped (or vice versa):** proceed
  with the audio-stream derivation (v0.2.34 §1.1's contract: the shipped
  MP4's timeline follows the *audio stream*, and the format value is the
  fallback of record) but append a run **warning** and record both figures
  in the diagnostic. One side unclassifiable is noise (e.g. format duration
  polluted by an odd attachment stream); both sides classifiable and
  disagreeing is signal. Tolerance justification: the 25% sanity band
  already bounds how wrong the format side can be; within that band a snap
  disagreement is by construction a *sub-4.3%* (neighbor-gap) disagreement —
  precisely the mis-measurement band the blind spot lives in.

Edge cases pinned by tests: audio extent under-reported 3 s in-band
(24.0337 → splits 24 vs 24000/1001 → refuse); honest 29.97 video source
with clean operands (both snap 30000/1001 → proceed); very short content
near the 10 s floor (format and stream extents both noisy → most likely one
side unsnappable → warn-and-proceed path, never a crash).

Where it runs: in the pre-flight, immediately after the existing snap
(`pipeline.py:932-949`, the FfprobeError-to-refusal wrap lands at 937), on CFR verdicts only (VFR already refused). Cost:
zero new probes — `probe_audio_duration_seconds` already resolves the
format duration internally for its 25% sanity; expose it on
`AudioDurationProbe` as `format_seconds: float | None` (additive dataclass
field, default None) so the pre-flight does not re-probe.

### C.4 Success-path diagnostic parity

Today only the rejection path (`_retain_rejected_mezzanine`'s diagnostic
JSON, `pipeline.py:385-433`) carries `format_duration` figures — a
successful run leaves no artifact recording the provenance comparison that

  chunks. The .rip purge preserves the .upscale tree when an upscale is

  gates are always rebuilt/re-run (concat is cheap; GPU hours are not).

  seconds can no longer snap to 24 and slip the clock gate.** The
  pre-flight now derives the rate twice - from the shipped audio
  stream's extent and from the container format duration - and REFUSES
  (fails open) when the two snap to different canonical rates. Successful
  runs record both figures in the run reasons for audit parity with
  rejection diagnostics.

### Added

- **The app's version is now visible everywhere a run is observed.** The

### Risks

1. **Heartbeat as a new background thread** — the first thread the stage
   spawns for bookkeeping (process drain threads already exist). Daemon +
   joined in `finally`; U-A2 pins no-leak. If the process is hard-killed the
   thread dies with it; no external state.
2. **Segment verify cost on full resume** — 57 × ~2-3 s decode-count = ~3
   min before the loop begins reusing. Acceptable one-time cost vs 5 GPU
   hours; surfaced via per-chunk `"resumed chunk"` steps so it never looks
   frozen (and each verify emits its step, so `updated_at` moves without
   the heartbeat even needing to fire).
3. **Manifest whole-file equality is strict** — a user who edits
   `chunk_seconds` between attempts (an unsupported knob today, plan-only)
   silently recomputes everything. Failing closed is correct; documented in
   the manifest field list.
4. **Cross-provenance guard refusal is a NEW refuse class on real discs** —
   bounded: it fires only when both derivations are snappable AND disagree
   (a sub-4.3% provenance disagreement), which is exactly the mis-measure
   band the blind spot lives in. The 2026-10-19 disc (both derivations snap
   24000/1001) is the P-C3 control; P-C4 pins the one-sided-noise
   warn/proceed path so odd containers are not refused.
5. **`step`-string matching in the health classifier** couples
   `upscale.py`'s step text to `monitor.py`'s set. Pinned both directions by
   P-A2/P-A4 using the real constants; a future rename fails visibly in CI.
   (Considered and rejected: a boolean `finalize` snapshot field — adds
   schema surface for no information the step set doesn't already carry.)
6. **CLI output during heartbeat** — clamped frac 0.999 means the CLI's
   `\r`-redraw loops one line per 15 s; no newline spam (P-A1 asserts the
   clamp; CLI behavior verified by its existing `frac >= 1.0` newline rule).
7. **Version surface drift** — the "single source" guarantee is only as good
   as its enforcement; T-D1/T-D2 make a hardcoded copy or a pyproject
