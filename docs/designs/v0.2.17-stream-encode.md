# v0.2.17 Design: fast mode — encode straight from disc

Status: design only (no code). Author: architect subagent, 2026-10-02.
Green-lit by Eric 2026-10-02 17:25: BOTH lanes — MakeMKV stream server
for Blu-rays (Lane A) first, libdvdcss direct-read for DVDs (Lane B)
second.

Today: `scan -> rip (.rip dir) -> probe -> encode from MKV -> OCR from
MKV -> mux subs`. v0.2.17 adds a **Fast mode (stream from disc)** toggle
on the Review page that skips the rip step entirely where possible.
Media access still flows through exactly one decryptor per lane
(MakeMKV for Blu-ray, libdvdcss for DVD); scan stays MakeMKV regardless
(title/stream inventory drives recommendations and the v0.2.15 override
combos).

Reading guide: Section 1 answers Q1 (the stream-server reality check
and its mandatory probe step); each remaining question gets its own
section labeled Q<N>.

---

## 1. Q1 — MakeMKV `stream` server: what is verified, what is not

### 1.1 What the official docs actually say

`https://makemkv.com/developers/usage.txt` (fetched during this design,
2026-10-02) documents:

```
Streaming options:
--upnp=true/false   Enable or disable UPNP streaming. Default: program preferences.
--bindip=address    Specify IP address to bind. Default: None (UPNP binds first
                    available; web server listens on all available addresses).
--bindport=port     Specify web server port to bind. Default: 51000.

Example: makemvcon stream --upnp=1 --cache=128 --bindip=192.168.1.102 \
            --bindport=51000 --messages=-none
```

That is the **entire** official documentation of stream mode. It says
nothing about:

- the per-title URL shape (community reports say the web server serves
  an index page at `/` and per-title MPEG-TS at `/title0.ts`,
  `/title1.ts`, ... matching the MakeMKV title indexes from a scan —
  **unverified**),
- the served container (community: `mpegts` — **unverified**),
- whether subtitle streams are included in the served TS (needed for
  our OCR path — **unverified**),
- whether the server honors HTTP range requests (decides whether
  ffprobe can probe quickly and whether ffmpeg can seek — **unverified**),
- how stream order in the TS maps to scan-side stream order (the whole
  `_audio_ordinal`/`_subtitle_ordinal` assumption in pipeline.py rests
  on "MakeMKV preserves per-type stream order in its outputs"; that
  contract is validated for MKV rips, **not** for the stream server).

**This documentation is thin. We do not design blind against this
surface.** Everything below in Sections 2–8 is written so the unknowns
collapse to a single runtime seam (`streamsource.py` URL resolution +
probe), and implementation does not start until the probe in 1.2 has
been run against a real disc and its output pasted into the milestone
issue.

### 1.2 The one-time probe (ships first, runs before implementation)

New CLI subcommand, shipping in v0.2.17 regardless of how the rest of
the feature lands:

```
bluray-to-mp4 probe-stream 0 --port 51000 --out probe-report.txt
```

Behavior (all local, no writes outside the report file):

1. Resolve `makemkvcon`, spawn
   `makemkvcon -r stream --cache=128 --bindip=127.0.0.1 --bindport=<port> --messages=-stdout`,
   poll `http://127.0.0.1:<port>/` with `urllib.request` (stdlib — no
   new dependency) until HTTP 200 or a 30 s timeout. Record raw HTML of
   `/` verbatim into the report.
2. Parse the index for candidate title URLs; ALSO brute-probe the
   community-reported shapes `/title0.ts` ... `/title{N-1}.ts` (N from
   our own `scan_disc`) plus a small set of alternates seen in forum
   posts (`/title0.m2ts`, `/Title/title0.ts`). Record HTTP status for
   each.
3. For each responding URL: run `ffprobe -v error -show_streams
   -show_format -of json <url>` with a 60 s timeout; record stream
   list (codec_type, codec_name, tags), format_name, and whether
   `duration` is populated (tells us if it behaves like a seekable
   file or a live stream).
4. Record ffmpeg `-demuxers`/`ffmpeg -protocols` excerpts so we know
   the probe ran against a capable binary.
5. Terminate the server (§7.1 lifecycle) and write the report.

Report goes into the milestone issue; the verdict branch is:

- **Green**: per-title TS URLs respond, ffprobe enumerates video+audio+
  subtitle streams, `format_name=mpegts`, duration present or readable
  → implement Lane A exactly as in §2.
- **Yellow**: URLs respond but no subtitle streams in the TS → Lane A
  ships with the §3 (Q2) fallback that extracts subtitles via a *rip
  of the subtitle stream only* (a sub-100 MB targeted rip — still far
  cheaper than a full rip); copy updated accordingly.
- **Red**: no usable per-title URLs → Lane A descoped, toggle hidden,
  report attached to the issue for a MakeMKV-forum follow-up. The
  probe subcommand and lifecycle machinery still ship (they are the
  diagnostic we will want in the field anyway).

### 1.3 Server startup parameters (Lane A)

Spawn, per run (not per title — one server serves every title):

```
makemkvcon -r stream --cache=128 \
    --bindip=127.0.0.1 --bindport=<picked port> --messages=-stdout
```

- `--bindip=127.0.0.1`: the server has **no authentication**. Binding
  to loopback means only ffmpeg/ffprobe on the same machine can reach
  it. Never bind 0.0.0.0; never expose it to the LAN. (The LAN monitor
  on 8765 is deliberately read-only and tokened; the stream server is
  neither.) Port-pick: try 51000 first (the documented default), then
  probe 51001–51009 for a free socket via `socket.bind()` before spawn.
- `--upnp`: omitted. DefaultUPnP announces a LAN media server; we want
  the opposite. If probing shows it defaults on, pass `--upnp=false`.
  (Probe step 1 records UPNP chatter in stdout, so we will know.)
- `--cache=128`: usage.txt's own recommendation for streaming.
- `--messages=-stdout`: robot-mode status lines stay parseable by the
  existing `parse_line`, so disc-open errors, beta-key expiry (MSG
  5021/5055), and MSG:5010 map onto the existing typed exceptions with
  zero new error classes.

### 1.4 Health-check / readiness

`GET http://127.0.0.1:<port>/` in a loop: 100 ms initial delay, 500 ms
interval, 30 s ceiling, tolerating `ConnectionRefusedError`/`URLError`
until the socket comes up. First HTTP 200 = ready. Failure modes:
timeout (drive spun down / server wedged → typed `StreamServerError`
with the captured stdout tail), process exit before ready (parse
stdout → `BetaKeyExpiredError`/`DiscOpenError` reuse).

## 2. Lane A architecture (Blu-ray, v0.2.17)

New module `bluray_to_mp4/streamsource.py`:

```python
@dataclass
class StreamServer:
    proc: subprocess.Popen
    port: int
    base_url: str            # http://127.0.0.1:<port>
    stdout_tail: deque[str]  # last ~50 robot lines for error context

def start_stream_server(binary="makemkvcon", *, cancel_state=None,
                        timeout=30.0) -> StreamServer: ...
def title_url(server: StreamServer, tid: int, disc: Disc) -> str: ...
def stop_stream_server(server: StreamServer, *, timeout=10.0) -> None: ...
def detect_dvdvideo(binary="ffmpeg") -> bool: ...   # Lane B feature probe
```

`title_url` is the **only** function that knows the URL shape; its
implementation is informed by the §1.2 probe report and unit-tested
against a captured fixture of the probe's index parse.

### 2.1 Pipeline changes (pipeline.py)

`run_pipeline` gains one keyword:

```python
fast_mode: bool = False
```

When `fast_mode and disc.media_type == "bluray"`:

1. After the plan/jobs loop (unchanged), call
   `start_stream_server()` once, before the per-title loop; wrap the
   whole job loop in `try/finally: stop_stream_server(...)` so no code
   path — success, job failure (C6), cancel, or crash — leaks a server
   (§7.2).
2. Per job:
   - `job.input_path = title_url(server, tid, disc)` instead of the
     `.mkv` path. Everything downstream already treats `input_path` as
     an opaque string passed to ffprobe/ffmpeg; URLs flow through the
     same calls unchanged.
   - The **verify/reuse/rip block simply does not run in fast mode** —
     with one exception (Q4, §5): if a *reusable rip already exists*,
     reuse wins and the server is not consulted for that title.
   - `probe_streams(job.input_path)` now probes the URL. Same function;
     the ProbedStream list it returns drives `nth_of_type` ordinal
     resolution **exactly as today**, so audio/subtitle mapping keeps
     one code path. (This is why §1.3 stream-order verification matters:
     if the served TS preserves per-type order — probe confirms — every
     v0.2.15 override and v0.2.13 fallback keeps working untouched.)
   - `execute_encode(job.encode_args, ...)` unchanged — ffmpeg reads the
     URL as input. One encode-side adjustment: add `-rw_timeout 15000000`
     (15 s I/O stall ceiling) and `-reconnect 1 -reconnect_streamed 1
     -reconnect_delay_max 5` for HTTP inputs so a transient read hiccup
     retries instead of instantly killing the encode; added by
     `build_encode_args` only when `plan.input_path` starts with
     `http` (a one-line branch, tested).
   - Encode progress math unchanged: `out_time_us` fraction of title
     duration is container-agnostic.
3. The `.rip` workdir is still created (subtitle intermediates and OCR
   scratch need it) but holds only tiny subtitle files in fast mode;
   the run-start purge and success-purge semantics are unchanged
   (§7.4).

When `fast_mode and disc.media_type == "dvd"`: Lane B (§8) — until Lane
B ships, the UI never presents this combination (§6), and the pipeline
raises a typed `FastModeUnavailableError` naming the reason (defense in
depth against a stale settings file forcing it on).

### 2.2 What deliberately does NOT change

- Scan, recommendations, series detection, TMDB, naming, stream
  overrides — all MakeMKV-scan-based, all identical.
- `build_encode_args` rate control, filters, sizing — identical; only
  the input token changes.
- OCR + mux (subtitles.py) — identical once it has its intermediate
  file (Q2, §3).

## 3. Q2 — subtitle OCR without a ripped MKV

**Chosen: option (a) — extract only the subtitle stream to a small
intermediate; encode stays fully streamed. Single-pass dual-output
ffmpeg is the default form.**

PGS subtitles are ~10–50 MB per title; VobSub less. The data volume was
never the problem — the only thing OCR needs is an input *file*.

Implementation: in fast mode, `execute_encode` runs ffmpeg with **two
outputs in one invocation**:

```
ffmpeg -y -hide_banner -nostdin \
    -reconnect 1 -reconnect_streamed 1 -reconnect_delay_max 5 \
    -rw_timeout 15000000 \
    -i http://127.0.0.1:51000/title0.ts \
    -map 0:v:0 -map 0:a:<ord> -c:v hevc_nvenc ... -f mp4  "D:\Movies\Movie.mp4" \
    -map 0:s:<ord> -c:s copy -f sup           ".rip\Movie_t00.sup"     # or:
    -map 0:s:<ord> -c:s copy -f matroska      ".rip\Movie_t00.vobsub.mkv"
```

One disc read pass, one decrypt traverse; the subtitle copy rides the
same bytes the encode already pulled. The `-f sup`/`-f matroska`
container choice reuses v0.2.16's `_intermediate_ext(codec_name)`
contract verbatim. After the encode, `run_subtitle_ocr(intermediate, 0,
video_out, ...)` is called with the *intermediate itself* as the input
(it is already a single-track file, so `extract_subtitles`'s inner
ffmpeg copy becomes trivially cheap; `stream_index=0`). OCR and the
mov_text mux then run exactly as in v0.2.16 — zero changes to
subtitles.py.

Fallback form (for the Yellow probe verdict or a real disc whose TS
drops the subtitle stream): a sequential second pass
`ffmpeg -i <url> -map 0:s:<ord> -c:s copy <intermediate>`. Costs one
extra full drive-read pass (~10–20 min at drive speed) but keeps the
feature whole.

**Rejected options:**

- (b) *Skip subtitles in fast mode*: regresses v0.2.16 — embedded subs
  in the MP4 just shipped and is the reason the feature exists for
  Eric. Unacceptable.
- (c) *Always rip when subtitles are on*: silently deletes the feature
  for every default configuration (subtitles are on by default). The
  toggle would be decorative.

Failure coupling note: because the subtitle extraction is a second
output of the encode invocation, an encode failure also forfeits the
intermediate. That is fine — OCR is meaningless without a video to
embed into — and keeps the failure model simple.

## 4. Q3 — failure coupling: a disc error at 70% now kills a 20-min encode

Today a scratched disc fails the rip in minute 2 with nothing lost.
Fast mode moves that same read error into the middle of the encode,
where it kills a partially-written MP4. Mitigations, in order:

1. **Cheap retry first.** ffmpeg's HTTP reconnect flags (§2.1) absorb
   sub-second stalls. On top of that, the pipeline classifies encode
   stderr/exit in fast mode: an I/O-class failure (exit code with
   "Input/output error", "Connection reset", or HTTP 5xx from the
   server log) triggers **one automatic in-place retry** of that
   title's encode (fresh ffmpeg invocation, `-y` overwrite of the
   partial MP4). Retry count and reason are recorded as a warning:
   `<name>: stream encode failed (disc read error), retried once`.
2. **Rip-mode fallback.** If the retried fast encode *also* fails with
   an I/O-class error, the job automatically switches to today's path
   for that title: full `rip_titles` → probe → encode, with a stage
   line `Fast encode failed twice - falling back to rip-and-encode for
   <name>` and a warning on the result. Non-I/O failures (encoder
   error, OOM) do NOT trigger fallback — a broken encoder would just
   break again; they record `job.error` and continue per C6.
3. **Partial-MP4 hygiene.** A failed fast encode leaves a truncated
   MP4 next to the output name. Before any retry/fallback, delete it
   (same fail-closed logic as the v0.2.12 per-file delete: ours alone,
   expected path). If all retries are exhausted the job errors out per
   C6 with the partial file removed — a clean "what's in the folder is
   what's finished" invariant holds.
4. **UI risk communication.** The toggle's tooltip (§7.3) says the
   trade in one sentence; the dry run prints it (§6.4). No modal
   warnings — the user opted in with an informed tooltip, and the
   automatic fallback means the worst case is *slower*, never
   silent-loss.

Retry budget is per-title, not global: a series disc with one bad
episode falls back once, and the episode reads clean.

## 5. Q4 — rip-reuse interaction

**Fast mode defaults to OFF whenever a reusable rip exists. Reuse wins
— it is strictly cheaper** (zero disc reading at all vs. a full-speed
encrypted re-read; an MP4 encode from an SSD-resident MKV cannot be
beaten by streaming from an optical drive).

Concretely, in fast mode, per title, before touching the server:

- If `job`'s expected `.rip/<title>.mkv` exists and passes the existing
  v0.2.12 (duration) + v0.2.15 (width) verification → **reuse it**, log
  `Reusing existing rip of <name> - fast mode skipped for this title`,
  and run the classic path for that job. Mixed lanes in one run are
  fine (title 1 streamed, title 2 reused).
- The run-start `.rip` purge is unchanged: unexpected files are still
  removed, expected reusable files still survive.
- The toggle's own default: the checkbox state persists (§6.2) as the
  user's *preference*, but each run computes its actual lane per title;
  the dry run reports which titles will stream and which will reuse.

## 6. Q5 + Q6 — stages, forecast, UI

### 6.1 Stage names (Q5)

Two new stage labels appear in fast mode; no stage is removed from the
classic path:

- `stream setup` — spawn + health-check of the stream server (one per
  run; typically 2–5 s including decryption init; stage line:
  `Starting disc stream server ...`).
- `encode` — unchanged label, now fed by the stream. The live ETA
  mechanism (`out_time_us` fraction) is container-agnostic and works
  unchanged.
- `ocr` — unchanged.
- `rip` — only appears in fast mode when reuse or §5 fallback engages.

`_run_stage`'s substring matching learns `"stream server"` →
`self._stage_now = "stream"`.

### 6.2 Forecast adjustments (Q5)

`_forecast_total_seconds` currently assumes `rip ≈ 5 min + d/40` per
upcoming job. In fast mode:

- Drop the rip term for streaming titles; add a one-time
  `STREAM_SETUP_S ≈ 30` constant at run start (forecast only, replaced
  by measured reality within seconds).
- Encode term: **slow the NVENC forecast multiplier from 6x to 4x** in
  fast mode. Rationale: today rip and encode are decoupled; in fast
  mode the encode's read throughput *is* the drive+decrypt throughput
  (MakeMKV decrypting at ~2x realtime caps a 6x encode at 2x). The x265
  term (1.5x) is unchanged — x265 is already slower than any realistic
  drive read. These are forecast-only guesses; the v0.2.14 mechanism
  swaps in the measured ETA at the first progress tick, so error bars
  close quickly. After validation runs we can re-tune the constants.
- OCR term `d/20` unchanged.
- Fallback-aware: when §5 rips in for a title, the rip ETA streams in
  live exactly like classic mode; the forecast for *remaining* titles
  still uses their planned lane.

### 6.3 UI (Q6): toggle placement, copy, persistence

Review page, Output card, row 1 — encoder combo gains a neighbor:

```
Output folder: [ D:\Movies                    ] [Browse...]
Encoder:       [ auto ▾ ]   ☑ Fast mode (stream from disc)
Include subtitles: [☑ OCR to .srt]            TMDB key: [........]
☑ LAN monitoring (Jarvis checks rip progress from the home server)
```

Toggle widget: `QCheckBox("Fast mode (stream from disc)")`.

Tooltip (exact copy):

> Skip the rip step and encode straight from the disc through MakeMKV's
> stream server. Faster end-to-end and uses almost no scratch disk.
> Trade-off: a disc error mid-encode restarts that encode from scratch
> (we retry once, then fall back to a normal rip automatically).

When the scanned disc is a DVD **before Lane B ships**: checkbox
disabled with tooltip `Fast mode for DVDs lands in v0.2.18 (direct-read
build); Blu-rays only today`. After Lane B ships, a DVD enables it only
when `detect_dvdvideo()` passes; otherwise disabled with
`This build's ffmpeg was compiled without libdvdcss - install the full
build or uncheck Fast mode for DVDs` (Q8, §8.4).

Persistence: `Settings.fast_mode: bool = False`, saved on Start with
the rest of the Review-page state (same save block as
`settings.encoder`). **Default off** — first-run behavior is today's
behavior; Eric flips it once and it sticks.

### 6.4 Dry-run message (Q6)

When `fast_mode=True`, each streaming job's dry-run warning block gains:

```
Fast mode: title <tid> will be encoded straight from the disc via
MakeMKV's stream server (no .mkv rip on disk). A disc error mid-encode
restarts that encode (one retry, then automatic rip fallback).
```

Reuse-titles print their classic plan unchanged plus `reusable rip
found - will not stream`. CLI dry runs print the same lines.

## 7. Q7 — Windows lifecycle, port collisions, dvdvideo URL, purge

### 7.1 Never leak a stream server

The morning's orphaned-makemkvcon incident is the design constraint.
Concretely:

- **Ownership.** The `_CancelState` class gains `stream_proc: Popen |
  None` next to its existing `proc`. `closeEvent` already cancels the
  run worker; the worker's `finally` calls `stop_stream_server`, which
  does `terminate()` → 10 s `wait()` → `kill()` (same budget ffmpeg
  gets in `execute_encode`). GUI close, cancel button, exception, and
  hard process exit (atexit-registered belt-and-suspenders cleanup)
  all route through it.
- **Startup collision.** Port pick binds a probe socket first
  (`socket.bind(("127.0.0.1", p))` close, then spawn) for p in
  51000..51009; all-busy → typed `StreamServerError("no free port in
  51000-51009; a leftover makemkvcon stream server may be running - end
  it in Task Manager")` — wording lifted from the v0.2.7 drive-timeout
  guidance pattern.
- **Detection of foreign servers.** If 51000 answers HTTP but we did
  not spawn it, we never kill foreign processes; we move to the next
  port. (Leftover *our* server: same treatment — next port wins; the
  stale one is orphaned-by-definition only until the machine reboots,
  and the atexit cleanup makes it rare. Documented in Troubleshooting.)
- **stdout drain.** The server's robot stdout is consumed on a daemon
  reader thread into a 50-line ring buffer, so a chatty makemkvcon can
  never deadlock on a full pipe (the classic Windows subprocess hang;
  the existing runner side-steps it by line-consume, we mirror with a
  bounded deque).

### 7.2 Purge interaction

Fast mode does not skip the v0.2.8/v0.2.12 purge — the `.rip` dir now
holds subtitle intermediates (`t00.sup` / `t00.vobsub.mkv`) instead of
50 GB MKVs, and the same "purge everything not expected by this run's
plan" logic applies unchanged. Success-purge still deletes the workdir
when all jobs complete. Fast mode's disk footprint in `.rip` is tens of
MB — the "skips the rip" promise is about the *video* bytes.

### 7.3 dvdvideo URL form (Lane B)

Verify in the Lane B probe (a second `probe-stream --dvd` variant run
on the real DVD drive), but current ffmpeg documentation says the form
is **not** a `dvd://` URL — it is a demuxer + device path:

```
ffmpeg -f dvdvideo -title <N> -i "E:" -map 0:v -map 0:a ...
```

with `-title` as a demuxer option (1-based title number), `-pgc` and
`-angle` available, and Windows input being the bare drive letter (the
demuxer resolves the device; `E:\` with backslash also accepted in
recent builds — the probe prints which form the CI-built binary
accepts). Our scan is 0-based MakeMKV tids ordered by duration; the
scan→`-title` number mapping must be proven by the probe (TINFO title
order vs. dvdvideo title numbering is **not** guaranteed identical;
probe lists both inventories side by side). Pipeline-side, Lane B sets
`job.input_path` to the drive letter and passes demuxer flags through a
new `EncodePlan.demuxer_args: list[str]` field (default `[]`), so URL
vs. drive-path differences stay out of `build_encode_args`' core.

### 7.4 Drive-letter capture

The UI already knows the drive (`DriveEntry.path` from `find_drives`).
The plan carries `"drive_path": "E:"` through to `run_pipeline` (new
kwarg, default None). CLI gains `--drive-path` for Lane B runs. If
absent on a DVD fast run, raise `FastModeUnavailableError("fast mode
needs the drive letter - rescan the disc")`.

## 8. Q8 — CI: the libdvdcss-enabled ffmpeg (Lane B, v0.2.18)

### 8.1 The legal/distribution frame

BtbN's `n8.1 win64-gpl` build deliberately excludes libdvdcss; VLC
ships it as a separate package for the same reason — CSS circumvention
is the legally cautious component, which is also why MakeMKV exists as
a separate user-installed tool today. Lane B changes our ffmpeg bundle
into a libdvd**css**-carrying binary. This is a private repo, personal-
backups framing (README's own disclaimer), and Eric's call stands
(17:25 green light). The design keeps the css build **opt-in at the
artifact level**: the main build continues to ship today's BtbN binary
by default (see split-build in 8.3).

### 8.2 Options weighed

1. **Compile ffmpeg from source in CI with `--enable-libdvdcss`
   (chosen).** windows-latest runner + MSYS2/MinGW toolchain:
   `pacman` installs `mingw-w64-x86_64-{toolchain,nasm,yasm,pkg-config}`,
   clone ffmpeg release/n8.1 + libdvdcss 1.4.3, configure
   `--enable-gpl --enable-libx265 --enable-libdvdcss --enable-nvenc
   --enable-demuxer=dvdvideo ...` mirroring BtbN's n8.1 flag set,
   static-link libdvdcss. Runtime cost: ~25–40 min uncached,
   **~1–3 min cached** via `actions/cache` keyed
   `ffmpeg-n8.1-dvdcss-1.4.3-<configure-flags-hash>-<runner-image>`.
   Pros: auditable build recipe in-repo, same trust level as building
   ourselves, zero third-party binary risk; the artifact is what we
   sign. Cons: build-script maintenance; the `dvdvideo` demuxer needs a
   recent-enough n8.x (it landed in ffmpeg 7/8 — the probe asserts its
   presence).
2. *Vendor a prebuilt libdvdcss ffmpeg* (e.g. from a community builds
   site). Rejected: unsigned third-party crypto-adjacent binary inside
   a code-signed release is exactly the supply-chain smell we removed
   by bundling BtbN; also violates "existing solutions preflight"
   hygiene given (1) works.
3. *Ship libdvdcss.dll alongside BtbN's ffmpeg.* Rejected: BtbN's build
   isn't configured to dynamically load it; dvdvideo links it at
   configure time. Non-starter.

### 8.3 Workflow shape (`.github/workflows/build-windows.yml`)

New job `ffmpeg-dvdcss` (matrix of one) that produces
`ffmpeg-dvdcss.exe` + `ffprobe-dvdcss.exe` artifacts; the main `build`
job downloads the artifact **as a sibling** rather than replacing
`ffmpeg.exe`:

```
packaging\tools\ffmpeg.exe           (BtbN n8.1 - unchanged default)
packaging\tools\ffprobe.exe          (BtbN n8.1 - unchanged)
packaging\tools\ffmpeg-css.exe       (in-house n8.1 + libdvdcss)
packaging\tools\ffprobe-css.exe
```

- Zip size impact: +~80–110 MB compressed for the second ffmpeg pair
  (each is ~75 MB). Acceptable; GitHub artifact limits fine. If size
  ever matters, ffprobe can stay single (the css probe and the BtbN
  probe return identical stream info for non-DVD inputs; but identical
  versions keep diagnostics simple — ship both).
- `binaries.resolve_ffmpeg` gains a Lane-B-only resolution: pipeline
  asks for `"ffmpeg-css"` **only** for a DVD fast-mode input; every
  other call keeps resolving plain `ffmpeg`. Discovery:
  `_app_internal_dirs()` already covers `tools/` — one `find_program(
  "ffmpeg-css", exe_names=["ffmpeg-css.exe"])` wrapper;
  `B2M_FFMPEG_CSS` env override follows the house pattern.
- CI verification step (mirrors the hevc_nvenc assert):
  `ffmpeg-css.exe -demuxers | Select-String dvdvideo` must match, and
  `ffmpeg-css.exe -h demuxer=dvdvideo` must exit 0, else the build
  fails.
- Cache invalidation is deterministic (key includes configure-flag
  hash), and a `workflow_dispatch` input `rebuild_ffmpeg: bool` forces
  a cold build for emergencies.

### 8.4 Graceful degradation guard

At app start (and re-checked with the Setup page's Re-check),
`detect_dvdvideo()` runs `ffmpeg-css -hide_banner -demuxers` (500 ms,
cached for the session — same spirit as the v0.2.16 NVENC probe cache)
and checks for ` dvdvideo`. The Setup page gains one **optional-row**
entry: `Fast DVD mode (libdvdcss ffmpeg)` — ok/missing with the plain
reason. When missing: DVD + fast-mode toggle disabled with the §6.3
tooltip; a config file that somehow forces it on raises
`FastModeUnavailableError` before any disc access. Blu-ray Lane A is
completely independent of all of this — no libdvdcss anywhere near the
MakeMKV stream path.

delivers the headline win (Blu-rays are the slow rips). Splitting keeps
v0.2.17 shippable even if Lane B's build takes iteration.

## 12. Open risks

1. **Stream-server surface is under-documented** (Q1, §1.1): URL
   shape, container, subtitle presence, header-seekability, and
   per-type stream order are all community-reported, not official.
   Mitigation: §1.2 probe gates implementation; failure path descopes
   cleanly to today's behavior.
2. **Drive throughput may cap encode speed**: fast mode couples read
   and encode; if MakeMKV decrypts at ~2x realtime, NVENC's 6x
   advantage partially evaporates (forecast already assumes 4x; real
   numbers come from validation). Worst case the feature is merely
   "no 25 GB scratch + less total wall time", still a win.
3. **Blu-ray BD+ behavior over stream**: the rip path has visible
   multi-minute BD+ open phases; whether stream mode repeats that open
   per title-URL hit or once per server start changes per-title
   latency. The probe measures this (step 3 timings are recorded).
4. **dvdvideo title-number mapping** (§7.3): scan tid → `-title N`
   correspondence is unproven until the DVD probe runs. A mismatch
   would silently encode the wrong title — the Lane B probe asserts
   it by duration comparison before the toggle ever enables for DVDs.
5. **libdvdcss distribution posture** (§8.1): the css-enabled binary
   only ships because the repo is private and the app is personal-
   backups scoped. If the repo ever goes public, the css artifact
   needs a legal re-think (documented here so the decision point is
   not lost).
6. **Subtitle presence in the served TS**: if MakeMKV's TS omits
   subtitle PIDs on some discs (Yellow verdict), the §3 second-pass
   fallback costs a full extra read pass on those discs. Acceptable;
   reported per run as a warning so we see it in History.
