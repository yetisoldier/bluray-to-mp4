# v0.2.18 Design: size-target slider (GB/hour) on the Review page

Status: design only (no code). Author: architect subagent, 2026-10-02.
Requested by Eric 2026-10-02 20:32: "add sliders so a user could adjust
the GB/hour output. Still have it default to what we are currently
using, but allow them to move it up or down in 250 MB increments."

Constraints: Python 3.14, PySide6 6.11, pytest, existing theme.py design
system, no new dependencies, novice-friendly copy, ~30-60 min
implementation.

---

## 1. UI control: what and where

### 1.1 Scope decision: one control per run, not per title

Eric's wording is "a user could adjust the GB/hour output" — this is a
quality knob for the run, the same mental slot as the existing
"Encoder:" combo. Per-title sliders (one per row in the tracks table)
would invite a novice to wonder "why would title 3 get more bits than
title 1?", and the pipeline's `EncodePlan` already carries one field
per job, so the one-run-value fans out cleanly. **One control on the
Review page, applying to every job in the run.**

### 1.2 Control choice: QSlider + value label vs QDoubleSpinBox

Both were weighed:

- **QSlider**: most visual, literally what Eric said ("sliders"). But
  QSlider is integer-only: 0.25 GB steps need the classic
  `slider = int((value - 0.5) / 0.25)` tick math with conversions in
  both directions, every bug in that glue produces an off-by-one
  tick label, and horizontal space is bounded (a Blu-ray movie page
  is already wide).
- **QDoubleSpinBox** with `setSingleStep(0.25)`, `setSuffix(" GB/hour")`,
  `setDecimals(2)`: exact values are honest (the user always reads the
  true number, no tick-to-value translation), arrows step in exact
  0.25 jumps, the field can be typed into, and theme.py already styles
  QSpinBox/QDoubleSpinBox (the same stylesheet block covers QSpinBox;
  QDoubleSpinBox inherits the QLineEdit chrome) — zero new visual
  language. Season/episode/year controls on the same page are already
  QSpinBox, so the pattern is established one card away.

**Recommendation: QDoubleSpinBox** (step 0.25, suffix " GB/hour",
`QAbstractSpinBox.CorrectionMode.CorrectToNearestValue`). Eric asked for
"sliders," but the actual requirement is "move it up or down in 250 MB
increments" — a spinbox with up/down arrows satisfies that exactly, with
no tick-math risk and a truthful numeric readout. If Eric pushes back
and wants the draggable feel after seeing it, the same model/value code
swaps to a QSlider + label in ~15 lines (the plumbing below is
control-agnostic; only the widget builder and one signal name change).
The doc names the widget `spin_gbph` either way.

### 1.3 Placement: the Output card, on the encoder row

The Output card (`_build_review_page`, main_window.py ~line 624) already
has a `QGridLayout` `row` with "Encoder:" at (1, 0-1) and
"Include subtitles:" at (1, 2-3). The new control joins that row:

```
row.addWidget(QLabel("Size target:"), 1, 4)
self.spin_gbph = QDoubleSpinBox()           # range 0.50-4.00, step 0.25
self.spin_gbph.setSuffix(" GB/hour")
row.addWidget(self.spin_gbph, 1, 5)
self.btn_gbph_reset = QPushButton("Reset")  # ghostBtn
row.addWidget(self.btn_gbph_reset, 1, 6)
```

Rationale: the user already looks at this row for "how will it encode";
size target belongs next to encoder, exactly where a novice expects
"quality/size" to live. The Reset button restores the disc-type default
(2.0 Blu-ray / 1.0 DVD) and doubles as the discoverable answer to "what
was the normal value?"

Grid columns 4-6 are unused on rows 0-3 today, so this is a pure
addition — no existing widget moves.

### 1.4 Projected-size label (live feedback)

A muted label directly to the right of the Reset button (or line 2 of
the same cell if width demands), updated on every value change and on
every rescan/preview refresh:

```python
self.label_gbph_projection = QLabel("")       # muted objectName
row.addWidget(self.label_gbph_projection, 2, 4, 1, 3)
```

Exact wording (movie case):

> 113 min -> about 1.9 GB total

Series case (sum over the planned jobs, matching what `_start_run`
already puts in `plan["jobs"][*]["duration_seconds"]`):

> 4 episodes, 172 min total -> about 2.9 GB total

Formula (one line, reusing `estimate_video_bitrate_kbps`'s inverse —
total budget is `gbph * hours` by definition; container slack and audio
are inside the gbph budget, so no extra terms):

```python
total_gb = gbph * sum(duration_s for each planned job) / 3600
```

Displayed with `total_gb:.1f` and minutes as `sum(duration_s) // 60`.
The label refreshes from `_update_previews` (it already recomputes the
planned-outputs list, so duration changes on rescan or episode edits
land automatically) and from the spin's `valueChanged`.

## 2. Defaults, range, and reset-on-rescan

### 2.1 Defaults and reset semantics

- Initial value = the current type default from encode.py:
  `BLURAY_GB_PER_HOUR` (2.0) or `DVD_GB_PER_HOUR` (1.0), resolved by
  `disc.media_type` — unless Settings has a per-type saved value (see
  Section 4), in which case the saved value wins.
- **Rescanning a different disc type resets the control to that type's
  effective default.** `_fill_review_page` already runs on every fresh
  scan and clears `_title_overrides`/`_stream_overrides`; the spin is
  re-initialized in the same method, sourced from
  `settings.extras["gbph_<media_type>"]` if present, else the encode.py
  constant. This matches the existing "overrides belong to this scan"
  contract while still honoring the per-type memory of Section 4.

### 2.2 Range: 0.50-4.00 GB/hour, step 0.25

- **Floor 0.50**: `estimate_video_bitrate_kbps` subtracts audio (up to
  640 kbps) and 3% container slack from `gbph * 2222 kbps`, so 0.50
  GB/hour leaves roughly 430 kbps of *video* bitrate for 6-channel
  audio — already near the point where 1080p HEVC visibly collapses.
  Below this the slider becomes a "make garbage" control; a user who
  truly wants smaller output is better served by resolution changes,
  which this app deliberately does not do.
- **Ceiling 4.00**: at 4.0 GB/hour the encode is ~8.4 Mbps video —
  visually transparent for 1080p HEVC from a BD master; higher values
  buy nothing measurable and multiply encode time on x265. One range
  for both disc types (not 0.5-2.0 for DVD, 0.5-4.0 for Blu-ray):
  a type-dependent range adds a hidden rule for zero real protection
  (a DVD at 3 GB/hour is wasteful but harmless; the projection label
  makes the waste visible), and one range keeps the widget static.
  The type default, not the range, carries the "DVDs want less"
  guidance.
- **Step 0.25**: Eric's exact request (250 MB increments).

## 3. Plumbing: Review spin -> plan -> worker -> pipeline -> EncodePlan

`EncodePlan.target_gb_per_hour: float | None` already exists; `None`
means "default by media type" via the `gb_per_hour` property. The
slider only fills a value that is currently always None. Full path:

1. **`MainWindow._start_run`** adds one key to the plan dict, read from
   the spin at Start time (same read-at-Start contract as
   `stream_overrides`, so mid-run UI edits can never race the worker):

   ```python
   plan["target_gb_per_hour"] = float(self.spin_gbph.value())
   ```

   The value is always written (never omitted), but see step 4: the
   pipeline treats "equals the media-type default" as None-equivalent,
   keeping dry-run output and EncodePlan reprs clean for untouched
   runs. Simpler option: only write the key when the value differs
   from the type default (`plan.pop`-style). **Pick: always write the
   key, let the pipeline normalize** — the UI stays honest (what you
   see is what runs) and the normalization lives in exactly one place.

2. **`RunWorker.run`** (ui/workers.py, in the existing `run_pipeline`
   call, next to `stream_overrides=`):

   ```python
   target_gb_per_hour=self.plan.get("target_gb_per_hour"),
   ```

3. **`run_pipeline` signature** (pipeline.py) gains one keyword:

   ```python
   target_gb_per_hour: float | None = None,
   ```

   Docstring line: "v0.2.18: Review-page size target. Explicit value
   wins over the media-type default; None (or a value equal to the
   disc's default) leaves EncodePlan on its built-in default."

4. **EncodePlan construction sites** — pipeline.py has two (dry-run at
   ~line 455, real-run at ~line 679). Both gain:

   ```python
   target_gb_per_hour=_resolve_gbph(target_gb_per_hour, disc.media_type),
   ```

   with a three-line helper at module scope:

   ```python
   def _resolve_gbph(value: float | None, media_type: str | None) -> float | None:
       default = DVD_GB_PER_HOUR if media_type == "dvd" else BLURAY_GB_PER_HOUR
       return None if value is None or abs(value - default) < 1e-9 else value
   ```

   Interaction with existing defaults: **explicit wins**; absent or
   equal-to-default collapses to None, which EncodePlan already maps
   to the media-type constant. No change to encode.py at all — this is
   the whole point of the `target_gb_per_hour: float | None = None`
   field that shipped before this design. Dry-run output therefore
   stays byte-identical for default runs (assertion-friendly), and a
   non-default run shows the override in the args' bitrate numbers,
   which the Section 7 dry-run test asserts on.

   Note: the real-run EncodePlan rebuild happens *after* rip/probe;
   passing the same computed value in both places keeps dry-run and
   real-run arg text identical, which the tests rely on.

## 4. Persistence: per media type in settings.extras

**Final call: persist per media type** in the existing
`Settings.extras` dict (already a free-form bag on the config
dataclass, survives `asdict` round-trips, no config schema change):

```python
settings.extras["gbph_bluray"] = 2.25   # written at Start time
settings.extras["gbph_dvd"]    = 1.25
```

Why this over the alternatives:

- **A single global value is a trap.** Eric re-rips the same disc
  repeatedly (the validation-day pattern), so persistence genuinely
  helps — but a single sticky number silently applies to the *other*
  disc type. A DVD ripped at a remembered 2.5 GB/hour triples its
  encode time for nothing. Per-key-per-type removes the trap entirely:
  each disc type remembers exactly its own slider.
- **Persisting an offset** (`+0.25` relative to default) is clever in
  the wrong way: the label, the plan, and History all speak absolute
  GB/hour, and an offset produces a different absolute value when the
  type default changes in a future release. Absolute per-type values
  are simpler to reason about and survive default changes.
- **Not persisting at all** makes Eric re-dial every run of the same
  disc — the exact workflow he has. Persisting is the point.

Write path: in `_start_run`, alongside the existing
`self.settings.encoder = ...; self.settings.save()` block:

```python
self.settings.extras[f"gbph_{self.disc.media_type or 'bluray'}"] = float(self.spin_gbph.value())
```

Read path: `_fill_review_page` sets the spin from the per-type key,
falling back to the encode.py constant; the Reset button writes the
constant back into the spin (and, on the next Start, into extras).

Validation: clamp the loaded value into [0.5, 4.0] and to a 0.25
multiple on read — hand-edited config.json must never produce an
out-of-range spin.

## 5. Live feedback details

Covered in 1.4; the single formula is
`total_gb = gbph * planned_seconds / 3600`, planned_seconds sourced
from the same `_plan_output_names()` pass `_start_run` uses, so the
number the user reads on Review is the number the run will target.
Rounding to one decimal matches the History page's existing
`gb_per_hour` presentation. No per-job breakdown (novice surface); the
movie and series formats in 1.4 are the complete spec.

## 6. History: target vs actual

**Include — it is cheap.** `JobRecord` (monitor.py) gains one field:

```python
target_gb_per_hour: float = 0.0   # v0.2.18: the run's size target; 0.0 = pre-slider record
```

`RunWorker.run` passes `self.plan.get("target_gb_per_hour")` (or the
resolved default when the key is absent) into `JobRecord` at
`job_done` time — the same block that already computes `size_bytes`.
The History table gains one narrow column "Target GB/hr" next to the
existing achieved-column, rendering `"{rec.target_gb_per_hour:.2f}"`
when non-zero and an em-dash-free "—"... no — an empty cell when zero
(old records). One dataclass field, one argument, one column: inside
the cost budget, and target-vs-actual is precisely the validation
number Eric checks by hand every run.

## 8. Rollout: v0.2.17 or v0.2.18

**Recommendation: land as v0.2.17 content if v0.2.17 has not shipped
to Eric's machine as a release zip when this is implemented; otherwise
v0.2.18.**

Rationale: v0.2.17 is *stream-encode* work (probe.5 mid-flight as of
this writing) — a high-risk lane with an unresolved runtime seam. The
slider is self-contained, touches only Review-page layout plus one
pipeline kwarg, and shares zero code with the stream lane. Coupling
them in one version number adds no merge risk either way (disjoint
files), but shipping the slider under the *whichever number is next*
rule keeps the changelog honest: if 0.2.17's zip is already built,
this is 0.2.18; if the zip is still pending, the slider rides 0.2.17
as a second bullet. No feature-flag or interlock needed in either
case. If forced to pick one number today: **v0.2.18** — release
hygiene beats version-number economy, and "stream encode" and "size
slider" are unrelated enough that mixing them under one heading would
make the changelog harder to scan for a novice.
