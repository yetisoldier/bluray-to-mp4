# v0.2.34 — Derived Stamp Rate for the DVD AI Upscale

**Status:** design (approved direction; Eric sign-off pending implementation)
**Author:** Bob (architect)
**Implements:** `plan.fps` derived from decode-truth
(`nb_read_frames / audio duration`, snapped to a canonical rate) instead of the
container's `r_frame_rate`/`avg_frame_rate` metadata; a restored clock-truth
gate (mezzanine duration vs rip audio duration) that composes with
`verify_mezzanine_frames`.
**Fixes:** the 2026-10-18 Mamma Mia HWA redo discovery: this disc reports
`r_frame_rate = avg_frame_rate = 30000/1001` on a soft-telecined film whose
163,509 decoded frames span 6,818.4 s of audio — a true 23.976 clock. v0.2.33
ships frame-exact extraction at 23.976 frames/s **but stamps reassembly with
the container's lying 29.97**: a 163,509-frame mezzanine at 29.97 plays in
5,453 s against 6,818 s of audio (~20% desync). `verify_mezzanine_frames`
passes (the count is exact; the *clock* is wrong), v0.2.33 deleted the
duration gate, so the desynced mezzanine would have encoded and shipped. The
container's rate fields are a lie source and must not set the stamp.

---

## 0. Root cause, precisely

v0.2.27 fixed a real desync by preferring `avg_frame_rate` over
`r_frame_rate` (`ffprobe.py:113-127`). That fix assumed one of the two
metadata fields tells the truth. Tonight's probe of the live redo rip
(`J:\.rip\C1_t10.mkv`) falsifies the assumption on this disc:

- `r_frame_rate = avg_frame_rate = 30000/1001` — both fields agree, both lie
  (soft-telecined film: stored at true 24000/1001, flagged for 29.97
  display).
- `nb_read_frames = 163,509` (full `-count_frames` decode, zero errors).
- Audio extent 6,818.4 s (film runtime 113.6 min; matches the 10/17 run's
  57 × 120 s plan).
- 163,509 / 6,818.4 = 23.9775 fps ≈ 24000/1001 (23.9760, delta 0.006%).

The v0.2.33 CFR pre-flight (`ffprobe.py:352-390`) compares `r` to `avg` —
on this disc they are equal, so it passes, correctly, by its own definition
(the container's *declared* clock really is constant). What `.33` never
checked is whether that declared clock matches the **decoded reality**:
frames ÷ time. `.34` makes decode-truth the authority and demotes the
metadata fields to diagnostics. This is a strict generalization of the `.33`
VFR refusal: `.33` refuses clocks that disagree with each other; `.34`
additionally refuses (or corrects) clocks that disagree with the decoded
frames.

## 1. Stamp-rate derivation (the core change)

### 1.0 Definitions

- **Stamp rate** — the `-framerate` token handed to the image2 mezzanine
  writer (`upscale.py:~612-627`, the `image2 -framerate plan.fps` segment
  reassembly). This is the *only* consumer of `plan.fps` that affects A/V
  sync; chunk bound math (`.33 §2.3`) uses the same value via
  `compute_chunk_frames`.
- **Decode-truth rate** — `rip_total_frames / audio_duration_seconds`,
  where both operands are measured, not metadata.

### 1.1 The audio-duration source of truth

The final encode maps audio from the original rip
(`encode.py:85-100`: `audio_input` is the rip, `-map {audio_input}:a:N?`).
Audio, not the container's video fields, is the playback clock the shipped
MP4 obeys. The derivation must therefore use **the duration of the audio
stream that will reach the MP4**.

New helper in `bluray_to_mp4/ffprobe.py`:

```
probe_audio_duration_seconds(path, audio_index: int | None, *, binary="ffprobe") -> AudioDurationProbe
```

Semantics:

1. **Selected audio stream extent (primary source).** ffprobe the selected
   audio stream's *measured* extent, not its metadata `duration` tag:

   ```
   ffprobe -v error -select_streams a:{N} -show_entries stream=duration \
     -of csv=p=0 <rip>
   ```

   `N` is the ordinal the encode will pass to `-map {audio_input}:a:{N}?` —
   i.e. `audio_ord or 0` resolved against the rip's layout
   (`pipeline.py:789-790` already selects this exact stream object; its
   ordinal within the audio set is `nth_ordinal(streams, audio)`,
   `pipeline.py:~1040`). When the encode plan would carry `audio_sid=None`
   (no stream selected — defensive; the pipeline currently raises first),
   probe `a:0`, matching encode's `-map ...a:0?` fallback.
2. **Format duration fallback (no-audio / probe failure).** When the rip
   has no audio stream at all, or the stream `duration` field is
   absent/unparsable, fall back to `probe_duration_seconds(path)`
   (`ffprobe.py:151-179`, the existing `format=duration` probe) and set a
   flag `duration_from_format=True` on the result. The diagnostic records
   the fallback so the operator can distrust it.
3. **Sanity minimums.** The derived rate is garbage when the denominator
   is garbage. Refuse (raise `FfprobeError` → `UpscaleError`, fail-open)
   before any GPU work when:
   - both the stream extent and the format duration are missing/unparsable;
   - the chosen duration is **≤ 0**, or **< 10 s** (a DVD title this short
     is a probe artifact, not a movie; it also guards the division against
     pathological rates like 163,509 / 0.2);
   - the chosen duration disagrees with the container format duration by
     **> 25%** when both exist (a broken stream extent — e.g. DTS core vs
     HD-MA passthrough mis-flagging — must not silently set the stamp;
     refuse and let the operator look). Justification: legit audio/video
     extent skew on DVD rips is seconds (lead-in/lead-out), never a quarter
     of the runtime, so 25% separates "normal skew" from "broken probe"
     with an order of magnitude of headroom.

The no-audio **path is not a refusal**: DVD rips without audio are not
this pipeline's case (the pipeline hard-errors earlier at
`pipeline.py:791-794` when no audio stream exists), but the helper must
still behave sanely standalone: format-duration fallback, same sanity
minimums, `duration_from_format=True` recorded.

**Why not the MakeMKV title duration?** `plan.duration_seconds` /
`title.duration_seconds` is an integer-second title-scan figure — the exact
lie adjacent to the one being fixed (`.33 §1` documents it as the drift
source the frame-exact rework retired). It is never consulted for the stamp
rate. It remains in the plan only as a human label and encode ETA input.

**Why not video-stream extent?** The video stream's `duration` field is a
container metadata value from the same family as the rate fields being
demoted; on this disc family it cannot be trusted. The audio stream's
extent is what the shipped MP4's timeline follows. (Format duration is the
*fallback*, used only when no trusted stream extent exists.)

### 1.2 Canonical-rate snap

Raw decode-truth rates are noisy at the fourth decimal (23.9775 vs the
canonical 23.9760 on this disc) because the audio extent and the frame
count measure slightly different things (audio streams carry container
lead-in/out padding the film doesn't have). Snapping to canonical rates
converts measurement noise into the exactly-correct clock.

New helper in `bluray_to_mp4/ffprobe.py`:

```
snap_to_canonical_rate(derived: float) -> (token: str, snapped: bool)
```

Canonical set (tokens as handed to ffmpeg `-framerate`):

| Token          | Float      | Class                    |
|----------------|------------|--------------------------|
| `24000/1001`   | 23.976023… | NTSC film (this disc)    |
| `24`           | 24.0       | integer film             |
| `25`           | 25.0       | PAL film/video           |
| `30000/1001`   | 29.970029… | NTSC video (true 29.97)  |
| `50`           | 50.0       | PAL double-rate          |
| `60000/1001`   | 59.940059… | NTSC double-rate         |

**50 and 60000/1001 belong in the set.** Real DVDs do carry 50i/59.94i
content (sports, concert, and documentary video sources, including PAL
50-field and NTSC 59.94-field discs). The pipeline's interlace/deinterlace
machinery (`is_interlaced`, `yadif`) already targets these. A video-source
disc decode-counted at 59.94 would otherwise be *unsnappable* and refused
— a false refusal of a legitimately-upscalable disc. They cost nothing to
include: the snap is a nearest-neighbor match with a relative tolerance,
and 50/59.94 are too far from every other entry (≥ 25% gaps) to ever
collide. **48, 72, 90, 120 do not belong**: vanishingly rare on DVD, and
each added entry is a new false-snap target for a noisy measurement. The
refusal path below covers anything outside the set honestly.

**Snap tolerance: 0.1% relative** (`|derived - canonical| / canonical
≤ 0.001`).

Justification against the neighbors that must *not* snap:

- This disc: 23.9775 vs 23.9760 = **0.0063%** — snaps with 16× headroom.
- True 29.97 video source, 163,509 frames over 5,453.0 s of audio →
  derived 29.9856 vs canonical 29.9700 = 0.052% — snaps.
- Nearest-neighbor separation in the set is 4.3% (24000/1001 vs 24). The
  tolerance is **43× tighter** than the smallest set-internal gap, so a
  snap is always unambiguous.
- The `.33` CFR verdict already uses 0.1% for the same class of
  "is this clock difference real or rounding" judgment
  (`probe_cfr_check`, `ffprobe.py:388`); keeping one tolerance constant
  for both decisions keeps the model coherent.
- A genuinely non-canonical clock — true 23.0 fps, true 26.2 fps —
  misses every entry by ≥ 0.1% and is **refused** (§1.3).

`snapped=True` records that the measurement was adjusted; the diagnostic
(§4) records both the raw derived rate and the snapped token so the
adjustment is auditable per run.

### 1.3 Unsnappable → refuse before GPU, fail-open

The `.33` VFR refusal established the shape: a rip whose clock we cannot
honestly name must not be rebuilt on a guessed constant clock. `.34`
extends the same rule to decode-truth:

- Derived rate within 0.1% of no canonical entry → **refuse**:
  raise `UpscaleError` naming the derived rate, the frame count, the
  duration source, and the nearest canonical candidate, *inside* the
  existing `try` in the upscale pre-flight so it hits the same fail-open
  handler (`pipeline.py:~925-949`). The encode ships the original rip with
  an honest warning; nothing is deleted. This is honest no in ~30 s of
  probes, not GPU hours — the `.33 §2.2` contract, generalized.
- The `.33` CFR pre-flight **stays** as a fast diagnostic capture
  (r/avg tokens recorded into the diagnostic as before), but its verdict
  is **no longer the gate** for the stamp decision. A `CFR` verdict with
  lying fields (this disc) now proceeds and gets stamped correctly; a
  `VFR` verdict still refuses (a genuinely variable clock cannot be
  reassembled at any constant rate — decode-truth averaging would hide,
  not fix, that; `nb_read_frames/total_time` of a VFR source is a
  meaningless average). Implementation note: the VFR/UNKNOWN refusal
  check runs first (unchanged), then the derived-rate snap runs on CFR
  verdicts only.

**Ordering inside the pre-flight** (the new sequence, all inside the
existing `try` at `pipeline.py:855-925`):

1. `probe_frame_count` → `rip_total_frames` (unchanged).
2. `probe_cfr_check` → refuse on `VFR`/`UNKNOWN` (unchanged).
3. **NEW:** `probe_audio_duration_seconds(job.input_path, audio_ordinal)`
   → `AudioDurationProbe(seconds, from_format)`.
4. **NEW:** `derived = rip_total_frames / seconds`;
   `token, snapped = snap_to_canonical_rate(derived)`; refuse when
   unsnappable.
5. **NEW:** `rip_fps = token` — replacing the metadata read at
   `pipeline.py:840-847` (`video_frame_rate(streams)` plus its
   29.97-fallback warning). The fallback-with-warning path disappears for
   the upscale plan: `.34` always knows the rate or refuses. (Step 2's
   UNKNOWN refusal already covers "rates not even nameable"; the stamp
   never falls back to a default.)

### 1.4 What `plan.fps` becomes

`UpscalePlan.fps` keeps its type (`str` token) and every consumer works
unchanged:

- `compute_chunk_frames(chunk_seconds, plan.fps)` (`upscale.py:377-389`)
  — sees the derived canonical token. On this disc:
  `round(120 × 24000/1001) = 2877` frames; `compute_chunk_bounds(163509,
  2877)` → 57 chunks (56 × 2877 + remainder 2397). This matches the
  observed 10/17 57-chunk plan exactly — the chunk count is *stable*
  across the fix because the lying container rate and the derived rate
  both sit in the NTSC family; the stamp is what changes, not the plan
  geometry. (Had the stamp stayed 29.97 with 23.976-speed frames, bounds
  would have been computed at 3596 frames/chunk — note `.33` shipped
  *both* errors: chunk sizing from the lie too. `.34` derives both from
  the same truth.)
- `ffmpeg -framerate plan.fps` in the segment writer
  (`upscale.py:~612-627`) — reassembly stamps each segment at the
  derived clock; the mezzanine's playback duration becomes
  `total_frames / 23.976 = 6,819.7 s` ≈ the 6,818.4 s audio. Residual
  1.3 s (0.019%) is the audio lead-in/out skew the gate (§3) tolerates.
- `verify_mezzanine_frames` and the per-chunk assertions — unchanged;
  they count, they don't clock.

`video_frame_rate` (`ffprobe.py:113-127`) is **not deleted and not
rerouted**: it still feeds the non-upscale encode path nowhere (encode
itself never stamps; ffmpeg reads the input), and its `.33` fallback
warning is retired only inside the upscale pre-flight, where the derived
rate replaces it. (If a future caller needs the metadata rate, the helper
remains; the upscale plan simply no longer *trusts* it.)

## 2. Chunk-plan interaction (design requirement 2)

The derived fps flows through the existing `.33 §2.3` machinery untouched:

```
F   = compute_chunk_frames(plan.chunk_seconds, derived_token)
    = max(1, round(120 × 23.976023…)) = 2877          # this disc
N   = 163_509
bounds = compute_chunk_bounds(N, F)                    # 57 chunks
       = [(0,2877), (2877,2877), …, (56×2877, 163509−56×2877=2397)]
```

Verification against the observed 10/17 plan: 57 chunks at ~120 s — the
`.34` plan reproduces it *for the right reason* (indexed frames at the
true clock), where `.33` reproduced it incidentally (indexed frames at the
wrong clock still happen to total 57 chunks at 120 s nominal because both
clocks are NTSC-family; the per-chunk frame *count* differed: 2877 true
vs 3596 stamped).

The tail-chunk and per-chunk assertion behavior is inherited verbatim:
last chunk remainder, `select='between(n,{first},{first+count-1})'`,
`-vsync 0`, PNG-count assertions in and out of Real-ESRGAN
(`upscale.py:460-520`). No seek-scope changes (`.33 §2.4`'s "no keyframe
seek scope creep" stands).

## 3. Clock-truth gate: `verify_mezzanine_clock` (design requirement 3)

`.33` deleted `verify_mezzanine_duration` because duration tolerances
cannot validate a *frame-exact* mezzanine — under a correct clock, counts
*are* the duration check. Tonight's evidence shows the hole: correct
count + wrong clock = wrong duration, and nothing downstream catches it.
The fix restores duration-equivalence **as a separate, composable gate**
on the clock dimension, deliberately not resurrecting the deleted
function:

- `verify_mezzanine_frames` asks *"did we rebuild every frame?"* (count
  axis; exact equality; `.33` semantics unchanged).
- **NEW** `verify_mezzanine_clock` asks *"does the rebuilt mezzanine play
  for as long as the audio we ship?"* (time axis; tolerance-based).

New function in `bluray_to_mp4/upscale.py`, placed beside
`verify_mezzanine_frames`, same injected-probe style:

```
def verify_mezzanine_clock(
    mezzanine_path: str,
    audio_duration_seconds: float,
    *,
    probe_duration,          # injected probe_duration_seconds-shaped callable
    tolerance_fraction: float = 0.001,      # 0.1% relative
    tolerance_floor_seconds: float = 2.0,   # absolute floor
) -> None:
```

Semantics:

- Probe the mezzanine's container duration via `probe_duration_seconds`
  (`format=duration` — the same figure ffprobe/player reports and the same
  helper the rip-reuse check uses; cheap, no decode).
- `tolerance = max(tolerance_floor_seconds,
  tolerance_fraction × audio_duration_seconds)`.
- `|mezz_duration − audio_duration| > tolerance` → `UpscaleError` naming
  both durations, the tolerance, and the derived stamp rate. The existing
  fail-open path (`pipeline.py:927-949`, unchanged) encodes the original
  rip, retains the rejected mezzanine, and writes the diagnostic.

Tolerance justification, against the two poles:

- **Too tight fails good mezzanines.** Legit audio/video extent skew on
  DVD rips: container lead-in/out, audio priming — seconds, not minutes.
  On this disc: mezzanine 6,819.7 s vs audio 6,818.4 s → delta 1.3 s.
  The gate's effective tolerance is `max(2.0, 6.82) = 6.8 s` — the good
  mezzanine passes with 5× headroom.
- **Too loose ships desyncs.** The failure being killed is *rate-class*
  error: 29.97 vs 23.976 stamps the same frames 25% apart → 1,366 s of
  delta on this disc. Any tolerance in the single-digit-seconds class
  kills it with two orders of magnitude of headroom. The relative 0.1%
  term scales to short content (a simulated 90-minute title tolerates
  5.4 s; the old `.31` gate's 0.5 s + 0.01% was the right shape — this
  keeps the shape, relaxes the constants, and pins *why*).
- Why not exact equality here (unlike the frames gate): durations are
  floats of different provenance (audio extent vs muxed container
  duration); sub-second wobble is normal and meaningless. The *count*
  gate owns exactness.

### 3.1 Composition, explicitly

The pipeline call site (after `verify_mezzanine_frames`, inside the same
`try`):

```
verify_mezzanine_frames(mezz_path, rip_total_frames, probe_frames=probe_frame_count)
verify_mezzanine_clock(
    mezz_path, audio_duration.seconds, probe_duration=probe_duration_seconds,
)
```

The two gates are orthogonal axes; either trip raises `UpscaleError` into
the *same* existing handler. The diagnostic (§4) gains the clock fields.
`verify_mezzanine_frames`'s contract is untouched — the `.33` pinned
tests (`tests/test_upscale.py:485-564`) keep passing byte-for-byte. The
old `verify_mezzanine_duration` is **not** reintroduced: it probed the
*rip's* duration from `plan.duration_seconds` (the title-scan integer,
retired in `.33 §1`) and gated pre-`.33` time-window chunking semantics;
`verify_mezzanine_clock` probes the *mezzanine* against the *audio
stream's measured extent* — same intent (clock truth), new operands, new
name so no stale caller/test can confuse them.

  "audio_duration_source": "stream" | "format",
  "audio_stream_ordinal": 0,
  "derived_rate_raw": 23.9775,

`r_frame_rate`/`avg_frame_rate` remain in the payload from `.33` (now

the derived truth). `_retain_rejected_mezzanine`
(`pipeline.py:~1249-1300`) receives these via the same `probe_ctx`
locals dict it already consumes — no signature change, new keys added to
`payload` only.

### Fixed

## 5. Regression fixtures (design requirement 5)

All synthetic/monkeypatched, consistent with suite style. The four
fixtures, with real numbers:

**(a) The Mamma Mia disc — the bug being fixed.**
Probe stubs: `r_frame_rate = avg_frame_rate = "30000/1001"` (container
lies, `.33` CFR verdict passes), `nb_read_frames = 163_509`, selected
audio stream duration `6818.4` s.
Expected: derived `163509/6818.4 = 23.9775` → snaps to `"24000/1001"`;
`plan.fps == "24000/1001"`; chunk math 2877/57; gates pass; encode maps
mezzanine video + rip audio; no warnings about frame rate (the *stamp*
decision is silent when it works; the metadata-vs-derived divergence is
diagnostic content, not user noise). This is the regression that fails on
shipped v0.2.33 (which would stamp `"30000/1001"`).

**(b) True 29.97 video source — control.**
Stubs: `r = avg = "30000/1001"`, `nb_read_frames = 163_509`, audio
duration `5453.0` s (163,509 / 5,453 = 29.9856 → 0.052% off canonical —
exactly what a real video-source disc looks like after audio-skew noise).
Expected: snaps to `"30000/1001"`; plan, chunking (3596/chunk),
reassembly all bit-identical to `.33` behavior on a truthful container.
This fixture *proves the fix is conservative*: a disc whose container
tells the truth keeps `.33`'s answer.

**(c) No-audio edge.**
Stubs: container has no audio stream → helper falls back to
`format=duration` (6818.4 s); `duration_from_format=True` recorded.
Expected: derivation proceeds identically to (a) at the same total; the
diagnostic records the fallback. Sub-cases pinned in the helper-level
test: format duration also missing → `FfprobeError` → pre-flight refusal;
format duration 5.0 s (< 10 s floor) → refusal; stream vs format extent
26% apart → refusal; 5% apart → proceeds with stream extent.

**(d) Unsnappable rate.**
Stubs: `nb_read_frames = 100_000`, audio `4000.0` s → derived 25.0 →
*snaps to `25`* (control that PAL works); then the actual case:
`nb_read_frames = 100_000`, audio `3800.0` s → derived 26.3158 → 0.1%+
from everything (nearest: 25 at 5.3%) → **refusal**:
`run_dvd_upscale` spy never called, warning names the derived rate and
nearest candidate, `execute_encode` ships the original rip, fail-open
warning present in `result.warnings`.

### Risks

1. **ffprobe `stream=duration` on some audio codecs** (DTS core inside
   HD-MA passthrough, odd PCM) can report the container value or nothing.
   Mitigation: 25%-skew sanity check + format fallback + refusal — never
   a silent guess. First real run should log the two values (the
   diagnostic records both).
2. **Short special features / title stubs** (~1-3 min) sit near the 10 s
   floor and the 2 s gate floor: tolerances were chosen so a 60 s feature
   still gates sanely (tolerance = 2.0 s floor). Verify on a short title
   in the first real batch (P-fixtures cover the math but not a real
   stream).
3. **`snap` mis-assigning a truly exotic-but-legit clock** (e.g. true
   23.0 fps telecine oddity) now refuses instead of encoding at a guessed
   rate — intended, honest, and cheap (30 s), but it is a *new* class of
   refusal on discs that previously... also shipped broken (`.33` would
   have desynced them). Acceptable; the warning names the derived rate so
   Eric can force-review.
4. **Performance:** one extra lightweight `stream=duration` probe per
   title (+1 ffprobe metadata call) and one `format=duration` on the
   mezzanine (~instant; muxed MKV, no decode). Negligible vs the existing
   two decode-count passes.
5. **Interaction with VFR verdict:** derived-rate snap runs only after a
   CFR verdict; a VFR source still refuses at `.33 §2.2` even if its
   average happens to snap — averaging a variable clock is a lie of
   averaging, not a stamp. Pinned by keeping `.33`'s VFR tests green
   (they are untouched; CI proves composition).
