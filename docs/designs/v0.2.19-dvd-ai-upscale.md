Status: design only (no code). Author: architect subagent, 2026-10-02;
second-opinion reconciliation folded in 2026-10-02 21:40 (ChatGPT review
pasted by Eric, reconciled by Jarvis; adopted items marked [2nd-op]).
Requested by Eric 2026-10-02 20:56: "add an optional AI upscale step for
DVD content to 720p BEFORE encoding", powered by his RTX 3090 Ti, with
two candidate paths (GPU-first NVIDIA VSR/DLPP or Real-ESRGAN

Subtitle Edit Windows zip via PyInstaller, novice-friendly, GPU = RTX
3090 Ti (driver 591.86, CUDA 13.1, NVENC API 13.0), bundled ffmpeg n8.1

exists (docs/designs/v0.2.18-gb-slider.md) and does not touch

## 1. Reality check: the two candidate paths on a 3090 Ti

Frame math first, because every number below hangs off it:

- 110-min NTSC DVD movie at 29.97 fps: **~197,800 frames**.
- Same movie after inverse telecine to 23.976p (most film-sourced
  DVDs): **~158,200 frames** (~20% cheaper; the [2nd-op]
  source-type detection in Section 3.4 is what makes this cheap case
  reliable rather than lucky).
- A 44-min series episode at 29.97: **~79,000 frames**.

### 1.1 Path 2 (model-first, realesrgan-ncnn-vulkan) throughput

Numbers below are engineering estimates from the ncnn/Vulkan model
characteristics and published community measurements of the same models
on 30xx GPUs (animevideov3 ~10 fps at 720p input on a 3080; x4plus
~0.5-1 fps at 1080p input on a 3090), scaled by pixel count to 720x480
input. They are **ranges, to be pinned by a probe run on Eric's actual
box before implementation hard-codes any ETA math** (the repo's
probe-culture pattern applies; see Section 6).

| model / route | input seen by net | est. fps on 3090 Ti (720x480 in) | wall clock for 110-min movie (upscale only) | VRAM |
|---|---|---|---|---|
| realesr-animevideov3, 2x | 720x480 | ~20-30 fps | **~2-3 h** | < 2 GB |
| realesrgan-x4plus at effective 2x (pre-resize 0.5x, net sees 360x240, out 1440x960) | 360x240 | ~8-12 fps | **~4.5-7 h** | 2-4 GB |
| realesrgan-x4plus at native 4x (out 2880x1920, then downscale) | 720x480 | ~3-6 fps | **~9-18 h** | 3-6 GB |

Plus the NVENC encode of the 720p result: hevc_nvenc at 720p runs
~300-500 fps on Ampere, so **~7-11 min** — noise next to the upscale.

Honest statement Eric asked for: **yes, a full movie takes hours.**
The fast animevideov3 route is an evening-per-movie (~2-3 h). The
general x4plus route at 2x is an overnight job (~5-7 h). x4plus at
native 4x is a day-long job and is **not recommended** — it buys no
visible quality over the 2x route for a 720p final target. VRAM is a
non-issue at SD resolutions on a 24 GB card (tiling would only matter
if we ever upscale 1080p content, which this option does not do).

Bottleneck note: the ncnn-vulkan CLI is directory-in/directory-out, so
real throughput includes PNG/WebP decode + GPU forward + encode +
disk I/O. The ranges above assume the standard `-j 1:2:2` pipeline
threads; the RTX 3090 Ti is never the whole story but at SD frame
sizes it stays the dominant term.

### 1.2 Path 1 (GPU-first, NVIDIA VSR / DLPP / "RTX SDK")

**This path does not exist as a scriptable product.** Details in
Section 2. Summary: VSR is a driver-embedded *playback* feature with no
offline/batch API; DLPP was removed from the Video Codec SDK years ago;
the RTX Video SDK is a Windows-native D3D11 developer library with a
developer-program license, no CLI, and redistribution terms that do not
fit a PyInstaller consumer zip. Even if integrated, it would not be
"the whole chain on the GPU with hevc_nvenc" any more than path 2 is —
in both paths the encode is hevc_nvenc either way. **Path 1 is
eliminated.** "GPU-first on the 3090 Ti" is satisfied by path 2: the
ncnn-vulkan binary runs the model on the same GPU that then does the
NVENC encode.

### 1.3 Sequential vs overlapped stages

The naive design runs upscale fully, then encode. Upscale is
GPU-compute-bound; NVENC encode is NVEnc-bound — the two use different
silicon. A pipelined design (encode each finished chunk while the next
upscales) would overlap ~10 min of NVENC per movie — 5% of runtime,
not worth the lifecycle complexity for v1. **Sequential stages.**

## 2. VSR / DLPP / DLSS video: what is and is NOT available

Precise inventory for a 3090 Ti on driver 591.86:

- **RTX Video Super Resolution (driver-embedded):** works on RTX
  20/30/40/50-series, quality levels 1-4 on 30-series. It is applied
  inside the driver to decoded video *at presentation time* — enabled
  per-GPU in the NVIDIA Control Panel/App and consumed by Chromium/
  Edge browsers and a handful of players (e.g., VLC via D3D11). There
  is **no supported API to run it as an offline file transcode**, no
  ffmpeg filter, no CLI. Community D3D11 capture hacks exist; none are
  redistributable or maintainable. **Not usable.**
- **DLPP (Deep Learning Post Processor):** an NVDEC-era post-processing
  feature from Video Codec SDK 8.x, deprecated and removed from the SDK
  years ago (current SDK shipped with our ffmpeg is 13.0). **Gone.**
- **RTX Video SDK (2025, developer SDK):** does exist and exposes
  VSR-class super-resolution to applications, but it is a Windows-only,
  D3D11-native C++ library, gated behind NVIDIA's developer program,
  requires an RTX GPU and recent driver, and its runtime-DLL
  redistribution terms are the SDK's own license — not a clean fit for
  a bundled consumer zip, and integrating a native D3D11 surface chain
  from a Python/Qt app means a C++ shim plus frame plumbing that dwarfs
  the rest of this feature. Technically possible; **disproportionate,
  rejected.**
- **"DLSS Video"/transformer-model SR:** the newer DLSS-class video
  announcements are driver/app features in the same playback-embedded
  family as VSR, not an offline SDK; some headline features target
  newer GPU generations first. There is nothing here to call from a
  batch pipeline on a 3090 Ti today. **Not usable.**

Bottom line for the design: the only viable, redistributable,
scriptable AI-upscale engine for this app on this hardware is
**realesrgan-ncnn-vulkan** (Vulkan compute, vendor-neutral as a bonus).

## 3. Quality expectations: honest read

### 3.1 Live-action DVD (realesrgan-x4plus, effective 2x, lanczos down to 720p)

What it does well: removes the MPEG-2 blocking and mosquito noise that
every 2000s DVD has, reconstructs edge detail better than any
conventional filter, and the 2x-supersample-then-lanczos-down route
yields genuinely crisper 720p than a straight lanczos 480p->720p.

Where it hurts: film grain is texture the model was not trained to
preserve — expect **haloing around grain-heavy areas, occasional
waxy/plasticky faces** in medium shots, ringing around rolling/ending
credits text, and invented micro-detail on out-of-focus backgrounds.
On a clean master (good DVD transfer, mild grain) the result is
"modestly but visibly better than lanczos." On a soft, noisy,
badly-authored disc the denoise/deblock gain is larger and the
artifacts are less objectionable — the worse the disc, the more this
helps.

Honest verdict for typical 2000s live-action DVDs: **"good, not
transformative."** It will not look like the Blu-ray. It will look
like the best possible 720p version of that DVD, with occasional
AI-flavored artifacts an enthusiast will notice in stills. Whether
that is worth 5-7 hours per movie is Eric's call to make per run —
which is exactly why this ships as a per-run opt-in, never a default.

### 3.2 Anime DVD (realesr-animevideov3, native 2x)

This is the model family this content was made for. Flat-color cel
regions denoise cleanly, line art is reconstructed crisply, and the
animevideov3 model is specifically tuned for *video* (temporal
compression artifacts), not just stills. Community results on DVD
anime are consistently strong — this is the single best use case for
AI upscaling that exists. Verdict: **genuinely impressive**, at the
fastest speed in the table (2-3 h/movie, ~40-60 min per 22-min episode
block... per 44-min episode ~1-1.5 h) and the lowest artifact risk.

### 3.3 Classify the source FIRST; deinterlace correctly — non-negotiable [2nd-op]

AI models must see progressive frames at the right geometry; feeding
interlaced 480i weaves combing artifacts into the model's own texture
and it will happily sharpen the comb teeth. But blind deinterlace is
equally wrong: running `yadif`/`bwdif` over a *hard-telecined*
film-source DVD doubles motion cadence artifacts into every output
frame and throws away the ~20% frame-count savings that inverse
telecine (IVTC) recovers. The second-opinion's key win — **source-
type detection BEFORE filtering** — is adopted:

**Detection (prepare step, before any filtering):**

1. ffprobe as the initial triage: `field_order` (tt/bb/progressive),
   `r_frame_rate` vs `avg_frame_rate` (24/30 patterns vs steady
   29.97), `nb_frames`, SAR/DAR.
2. Frame inspection on a 60-second sample to confirm: `idet`
   statistics plus a visual comb check on high-motion frames. The
   three-way verdict:
   - **Progressive** (already 23.976/24/25p, e.g. well-authored PAL
     or properly flagged NTSC film): no deinterlace at all.
   - **Hard 3:2 telecine** (film NTSC, combed frames in a 3:2 field
     cadence): IVTC — fieldmatch + decimate to 23.976:
     ```
     ffmpeg -i in.mkv -vf "fieldmatch=combmatch=full,bwdif=mode=send_field:deint=interlaced,decimate" -r 24000/1001 ...
     ```
     (fieldmatch recovers the progressive frames; bwdif in
     send_field/deint=interlaced only cleans the frames fieldmatch
     can't perfectly weave; decimate drops the duplicated field frame
     back to 23.976.)
   - **Genuine interlace** (native 29.97i video: TV studio video,
     concert discs, sports, extras shot on video): deinterlace to
     field rate 59.94 for temporal fidelity:
     ```
     ffmpeg -i in.mkv -vf "bwdif=mode=send_field:parity=auto",fps=60000/1001 ...
     ```

The pipeline already detects interlacing via `is_interlaced()` and
inserts `yadif` for the normal encode path, so the *concept* exists;
the upscale path replaces that single bit with the three-way
classification above, applied in the prepare sub-stage. No blind
deinterlace.

### 3.4 2x-then-downscale, square-pixel normalization, and the IVTC bonus

480p -> 720p is exactly 1.5x; ESRGAN models are fixed-ratio. The two
viable constructions:
- **Supersample route (recommended):** ESRGAN 2x to 1440x960, then
  lanczos down to 1280x720 (anamorphic-safe: scale to -2:720).
  Extra sharpness for free; this is the standard practice.
- animevideov3 also supports direct 2x — identical geometry.

**Square-pixel normalization [2nd-op]:** DVDs are anamorphic — stored
with non-square pixels (NTSC 720x480 ~ SAR 32:27/8:9; PAL 720x576 ~
SAR 64:45/16:15). ESRGAN models assume square pixels, and the AI
stage must see the *displayed* aspect ratio, not the stored one. The
prepare step therefore applies `setsar=1` with explicit per-format
geometry **before** the AI stage:

| source | displayed size (square pixels) | aspect |
|---|---|---|
| NTSC 720x480, 16:9 | 854x480 | 16:9 |
| NTSC 720x480, 4:3 | 720x540 | 4:3 |
| PAL 720x576, 4:3 | 768x576 | 4:3 |
| PAL 720x576, 16:9 | 1024x576 | 16:9 |

The ESRGAN 2x output (e.g. 1708x960, 1440x1080, 1536x1152, 2048x1152)
then lanczos-downscales to the matching 720p-frame geometry
(1280x720 or 960x720) instead of blindly assuming 854x480 input.

**IVTC bonus (Section 3.3's telecine arm):** most film-sourced DVDs
are telecined 23.976. Recovering 23.976p cuts frame count ~20% and
eliminates deinterlace artifacts entirely — and with the adopted
three-way detection it is now safe to take, because telecine is only
chosen when field-cadence inspection confirms it (mixed/anime content
falls through to the genuine-interlace arm instead of being mangled).

## 4. Recommended architecture

### 4.1 The stage and its placement

A new optional **Upscale stage** between rip and encode, per title:

```
rip -> probe -> [UPSCALE: deinterlace+extract -> ESRGAN -> mezzanine] -> encode -> OCR/mux
```

- DVD media type only; the control is hidden/disabled on Blu-ray scans
  (a 1080p upscale is a different hardware/time conversation; do not
  open it accidentally).
- Per-run selection on the Review page, Output card, next to the
  v0.2.18 Size-target spin: **"AI upscale:" dropdown: Off / 720p /
  720p (anime)**. Default **Off**, every scan, no persistence of the
  On state (a 5-hour surprise must never come from a stale setting).
- When non-Off is selected, the v0.2.18 size-target spin **raises its
  DVD default to 1.5 GB/hour for this run** (Eric's pairing rule: the
  option and the target move together). It sets the slider's value, it
  does not bypass it — the user can still move the spin, Reset still
  means "disc-type default" (1.0), and the per-type `extras`
  persistence from v0.2.18 is **not** polluted by the upscale default
  (the 1.5 is applied to the spin in-memory for the run; what gets
  persisted at Start time is whatever the user actually left in the
  spin, which is the existing v0.2.18 contract).

### 4.2 Intermediate files and temp space

The ncnn-vulkan CLI is directory-to-directory only (no reliable
stdin/stdout pipe), so the upscale stage is chunk-based:

1. ffmpeg decodes the ripped MKV through the prepare chain — source-
   type classification (Section 3.3: progressive / fieldmatch+decimate
   IVTC / bwdif field-rate), square-pixel normalization (Section 3.4
   `setsar=1` + display-geometry table), FPS-settle — into
   `UPSCALE_TMP/<tid>/in/NNNNN/` as JPEG (q95) frames, ~2000-frame
   chunks (`-f segment`).
2. realesrgan-ncnn-vulkan runs chunk dir -> chunk out dir, WebP output
   (lossless webp; ~3-5x smaller than PNG, natively supported by the
   binary), model = x4plus (live-action entry) or animevideov3 (anime
   entry), `-s 2`, `-f webp`.
3. ffmpeg assembles the upscaled chunk into a **video-only mezzanine
   MKV** (FFV1 or high-bitrate HEVC; FFV1 is lossless and cheap at SD,
   ~15-25 GB per movie — sized once, deleted at stage end) and the
   chunk's in/out frame dirs are deleted immediately.
4. Repeat per chunk; concatenate mezzanine segments (concat demuxer)
   into one upscaled intermediate per title.

Peak extra disk beyond today's rip: one chunk of frames (~1-2 GB) plus
the growing mezzanine (~15-25 GB for a 110-min movie at 720p FFV1;
less if HEVC mezzanine is chosen). **Budget: ~30 GB free in the
workdir for a movie.** The workdir inherits the existing `.rip` dir
(which v0.2.16 already keeps on failure and purges on success) —
upscale temp lives in a sibling subtree and follows the same
retention contract: kept on cancel/failure for debugging, deleted on
full success.

The encode stage then maps **video from the mezzanine, audio from the
original ripped MKV** (two `-i` inputs; `-map 0:v:0 -map 1:a:N`) — the
ESRGAN stage never touches audio, and `build_encode_args` gains an
optional `video_input_path` seam rather than a forked builder.

### 4.3 Progress, cancel, and the monitor

Progress reuses the existing tuple contract with a new stage name:
`("upscale", tid, frac, eta)` where frac is completed-frames/total-
frames (total = duration * classified output fps — 23.976 after IVTC,
59.94 for genuine interlace, native for progressive — honest to ~1%,
like the encode stage's 0.2% ETA warmup). Stage strings: "Upscaling <name>
(ai, chunk k/n) ...". The monitor's `stage`/`progress` fields already
carry arbitrary strings; the UI progress label maps "upscale" the same
way it maps "encode" (one new case).

Cancel: the same `cancel()` callable polls between chunks (cheap kill,
sub-second) and mid-chunk via process termination (realesrgan +
ffmpeg segmenter are child processes; terminate, then wait/kill with
the same 10 s discipline `execute_encode` uses). Partial chunk
artifacts are cleaned on cancel; the completed-chunk mezzanine stays
inside kept-intermediates on failure.

### 4.4 Failure handling: fail-open with a loud warning

If the ESRGAN binary errors, a chunk fails verification, or the GPU
driver falls over mid-stage: **record a red-level warning, discard the
upscale partial, and encode the title from the original rip at the
normal (non-upscaled) path**, exactly the C6 per-job isolation pattern
("job failed -> recorded -> queue continues"). Rationale: upscale is a
cosmetic enhancement; it must never turn a working movie into no movie.
The History row shows the fallback clearly. Eric can re-run with
upscale later — the same re-rip/reuse machinery already makes that a
cheap retry.

Contrast: a *cancel* is not a failure and still propagates
EncodeCancelled immediately, as today.

### 4.5 Dry run

`dry_run=True` reports the planned upscale stage (model, route,
estimated frame count, estimated wall clock range from Section 1.1,
peak-temp estimate) in the plan without running anything — the
existing dry-run pattern extended by one stage block. This is where a
novice discovers "this run will take ~6 hours."

## 6. Sequencing, effort, risk, and the probe step

**Sequence: v0.2.19**, after v0.2.17 (stream-encode; probe.5 owns its
lane and this design touches nothing in it) and v0.2.18 (GB/hour
slider — this feature *depends* on the slider contract: the 1.5
GB/hour pairing is a value written into that control, so it must land
second).

**Probe/benchmark step first (before implementation), same culture as
probe.3/4/5 — content and acceptance protocol upgraded per [2nd-op]:**
a one-afternoon benchmark harness Eric runs once on his box:

1. **Representative samples:** extract 30-60 s sections from real DVD
   rips chosen to stress what ESRGAN actually does wrong — close-up
   faces, fast motion, small/hard-edged text (credits, chapter cards),
   heavy-grain scenes. Not one convenient scene; a reel.
2. **Throughput probe (as originally scoped):** time
   x4plus-at-effective-2x and animevideov3-2x on the samples;
   converts Section 1.1's ranges into the actual ETA constants the UI
   and dry-run copy use. ~30 lines of throwaway script; the probe's
   own docs pattern applies.
3. **Head-to-head backend trial [2nd-op]:** run the same samples
   through a **TensorRT FP16 test harness** — ONNX export of
   RealESRGAN_x2plus + the anime model, driven by a standalone script
   on Eric's box (PyTorch/ONNX -> torch2trt/`trtexec` or
   TensorRT python bindings). This harness is a benchmark-only tool:
   **not shipped in the zip, not part of the app.** Record both
   throughputs (fps per model). Expected outcome is TensorRT ahead by
   2-4x on the 3090 Ti; if the win is material, spec TensorRT FP16 as
   an **optional fast mode for a later release** with the packaging
   cost stated honestly: the TensorRT Python stack is hundreds of MB,
   CUDA-version-coupled, and engine builds are per-resolution one-time
   compiles — versus the shipped baseline's 1.5 MB MIT ncnn exe with
   zero runtime deps. The benchmark decides with numbers; the design
   does not pre-commit.
4. **Quality acceptance, in playback not stills:** for each sample,
   compare the AI result against a **plain lanczos upscale to the same
   final 720p with identical encode settings** and decide by watching
   them. Reject criteria (from Section 3.1's honest read): waxy/
   plasticky faces, unstable/shimmering textures, haloing that
   distracts in motion. Stills flatter AI upscalers; playback is where
   the artifacts live. The whole feature is a per-run opt-in cosmetic
   enhancement — if it does not beat lanczos in playback on Eric's own
   discs, the honest verdict may be NO-GO, and this protocol is what
   makes that call defensible.

**Effort estimate:** 2-3 focused sessions after the probe —
1. `upscale.py` stage module (chunking, ESRGAN runner, mezzanine
   assembly, cancel) + binaries resolver: ~300 lines, the bulk.
2. Pipeline seam + encode two-input mapping + UI dropdown + size-spin
   pairing + progress/monitor wiring: ~120 lines across pipeline.py,
   encode.py, main_window.py, workers.py.
3. Tests (chunk flow with a fake ESRGAN runner, fallback-on-failure,
   dropdown->plan->EncodePlan propagation, slider pairing, dry-run
   block) + real-DVD validation run on Eric's hardware.

**Risk: medium.** New-code concentration is in one new module with a
clean seam; the risky parts are lifecycle (long-running child
processes, 30 GB temp, cancel mid-chunk) and expectations (hours-long
runs in a novice UI), both mitigated by the probe constants, the dry-
run honesty block, and fail-open fallback. No risk to the existing
encode path — it is untouched when the dropdown says Off.

## 7. Decision

- **Live-action collections (realesrgan-x4plus -> 720p): GO-WITH-CAVEATS**
  — it produces the best 720p a DVD can give, but it costs ~5-7 h per
  movie and adds grain-halo/waxy-face artifacts a picky eye will see,
  so it ships strictly per-run opt-in with a dry-run time warning.
- **Anime collections (realesr-animevideov3 -> 720p): GO**
  — the model class is purpose-built for cel content, results are
  consistently strong, and it is the fast route (~2-3 h per movie,
  ~1-1.5 h per episode) with the lowest artifact risk.
- **NVIDIA VSR/DLPP path: NO-GO**
  — there is no scriptable or redistributable offline API for it on a
  3090 Ti at driver 591.86; that path is eliminated, not deferred.

Overall: **GO-WITH-CAVEATS, implemented as the v0.2.19 design above**
— model-first via realesrgan-ncnn-vulkan, bundled (~75 MB), per-run
opt-in on the Review page, 1.5 GB/hour paired default through the
v0.2.18 slider, classify-then-prepare (progressive / IVTC / genuine
interlace) with setsar=1 normalization, chunk-based with fail-open
fallback, gated on the benchmark-afternoon protocol (representative
samples, ncnn-vs-TensorRT head-to-head, AI vs lanczos playback
acceptance) on Eric's machine.

## 8. Second-opinion reconciliation (ChatGPT review, 2026-10-02)

Eric pasted an external review tonight; Jarvis reconciled it. This
section records what was adopted, what was rejected, and why — the
design body above already carries the adopted items inline (marked
`[2nd-op]`).

### 8.1 Adopted

1. **Source-type detection BEFORE filtering** (Section 3.3): three-way
   classification — progressive / hard 3:2 telecine (fieldmatch +
   decimate to 23.976) / genuine interlace (bwdif, field-rate 59.94)
   — driven by ffprobe fields (`field_order`, r/s/avg frame rates,
   SAR/DAR) as the initial check plus 60 s frame inspection. No blind
   deinterlace. The pasted ffmpeg recipes are adopted verbatim as the
   reference chains (`fieldmatch=combmatch=full,bwdif=mode=send_field:
   deint=interlaced,decimate` and `bwdif=mode=send_field:parity=auto`
   + `fps=60000/1001`). This also upgrades the IVTC bonus from
   "v1.1 refinement" to a v1 arm, because the classification is what
   makes telecine handling safe.
2. **Square-pixel normalization** (Section 3.4): `setsar=1` + the
   explicit geometry table (854x480 16:9 NTSC, 720x540 4:3 NTSC,
   768x576 4:3 PAL, 1024x576 16:9 PAL) applied in the prepare step
   before the AI stage.
3. **Benchmark-afternoon protocol upgrade** (Section 6): 30-60 s
   representative sample sections (faces, motion, small text, grain);
   the AI result compared against a plain lanczos upscale at the same
   final resolution and identical encode settings; acceptance decided
   in playback, not stills; explicit reject criteria (waxy faces,
   unstable textures, visible halos in motion).
4. **Head-to-head backend trial inside the benchmark afternoon**
   (Section 6): baseline realesrgan-ncnn-vulkan (Vulkan) vs a
   TensorRT FP16 harness (ONNX export of RealESRGAN_x2plus + the
   anime model) driven by a standalone script on Eric's box — a probe
   tool, **never shipped in the zip**. Both throughputs recorded; if
   TensorRT wins materially (expectation: 2-4x on the 3090 Ti), it
   gets specced as an **optional fast mode for a later release**, with
   the packaging cost stated honestly: the TensorRT Python stack is
   hundreds of MB and CUDA-coupled, versus the baseline's 1.5 MB MIT
   ncnn exe with zero runtime deps.

### 8.2 Verified and declined: REAL Video Enhancer (RVE) as the engine

The pasted advice's claim was checked definitively against
<https://github.com/TNTwise/REAL-Video-Enhancer> (v2-main,
2.4.1). **Verdict: the "GUI-only Avalonia app" expectation is wrong
— RVE v2 exposes a real headless CLI**, `backend/rve-backend.py`,
with a full argparse interface: `-i/--input`, `-o/--output` (incl.
`PIPE`), `--upscale_model`, `--backend {pytorch,ncnn,tensorrt}`,
`--benchmark`, `--video_encoder_preset` (libx264/libx265/*nvenc*/
ffv1/...), plus batch processing via a .txt job list. It is not
GUI-only.

Honestly reassessed against realesrgan-ncnn-vulkan for our pipeline
despite that:

- **License:** RVE is **AGPL-3.0**; the ncnn exe and models we ship
  are MIT/BSD. Embedding RVE as our pipeline's engine and
  redistributing it inside a commercial-adjacent consumer zip drags
  AGPL copyleft obligations into the distribution story. We decline
  that on principle for an engine.
- **Footprint vs our zip:** RVE's ncnn backend wants a portable-python
  runtime + pip-managed backend + downloaded models (their own README:
  ~1 GB storage minimum; TensorRT path ~16 GB). Our shipped baseline
  is a 1.5 MB MIT exe + ~72 MB of version-locked models with zero
  runtime deps. Even RVE's own FAQ recommends ncnn as the fallback
  when TensorRT/PyTorch installs go wrong.
- **The CLI is an internal interface, not a stable API:**
  `rve-backend.py` is the process the GUI spawns — its flags include
  GUI-wiring details (`preview_shared_memory_id`,
  `pause_shared_memory_id`), it downloads its own ffmpeg when not
  given one, and there is no versioned, documented backward-compat
  contract for external callers. Building our zero-touch pipeline on
  another app's GUI-spawn boundary trades one babysitting surface for
  another. Our hard requirement is a runner we ship, pin, and control
  — for exactly the reason run 12 tonight (the OCR babysitting
  defect) demonstrated: unsupervised automation must own its whole
  chain. RVE's CLI is real, but adopting it means adopting its whole
  stack and maintenance surface; that reintroduces the same class of
  fragile-external-dependency failure, just in a different shape.
- **It would not remove our work anyway:** telecine classification,
  setsar normalization, chunked mezzanine, per-run pairing, cancel,
  fail-open, progress, and the benchmark protocol are all ours
  regardless of which inference binary sits inside them. ncnn remains
  the right engine. **Declined with the CLI finding honestly on the
  record.**

### 8.3 Rejected: x264 CRF-18 for the final encode

The pasted advice recommended a final x264 CRF-18 encode. **Declined,
spec-conflict:** the product spec is HEVC (hevc_nvenc/x265) and the
v0.2.18 GB/hour size targets — including this design's 1.5 GB/hour
paired default — were built and validated around HEVC encoders. x264
at comparable perceptual quality roughly doubles output size against
those targets, which is a silent double of the user's negotiated
storage contract, not a neutral encoder choice. If a specific disc
ever validates worse on hevc_nvenc than x264 in the playback-acceptance
protocol, that is a per-title encode-settings bug to file, not a
reason to change the codec floor.
