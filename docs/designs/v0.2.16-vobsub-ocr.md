# v0.2.16 Design: DVD VobSub subtitle OCR

Status: design only (no code). Author: architect subagent, 2026-10-02.
Scope: one bug fix - the first real DVD run (2026-10-02) encoded fine and
the v0.2.13 fallback correctly found subtitle stream 7 in the ripped MKV,
but OCR failed with:

    subtitle extraction failed: [sup @ ...] sup muxer supports only codec
    hdmv_pgs_subtitle for type subtitle / [out#0/sup @ ...] Could not write
    header (incorrect codec parameters ?): Invalid argument

Root cause: `run_subtitle_ocr` hard-codes a `.sup` intermediate filename
(Blu-ray PGS). DVDs carry VobSub (`dvd_subtitle`); ffmpeg's `sup` muxer
is PGS-only and writes nothing for codec `dvd_subtitle`.

Constraints: Python 3.14, PySide6, pytest; no new dependencies (no
mkvextract/MKVToolNix, no subtitle Edit bundle change - the CI workflow
`.github/workflows/build-windows.yml` is untouched). PGS path behavior
must not change.

---

## 1. The format facts (all verified on the dev box, 2026-10-02)

- `ffmpeg -muxers`: `sup` is `raw HDMV Presentation Graphic Stream
  subtitles`; there is **no vobsub muxer** at all. `-demuxers` does list
  `vobsub` (read-only). The commonly suggested
  `ffmpeg -i in.mkv -map 0:N -c copy out.idx` **cannot produce a
  `.sub`/`.idx` pair** - ffmpeg has nothing to write it with.
- `dvd_subtitle` is a subtitle codec (S) with an encoder listed, but no
  container muxer accepts it except the general-purpose MKV muxer.
- `matroska` muxer accepts `dvd_subtitle` for `-c:s copy`.
- Subtitle Edit 5.2.0 (already bundled by CI, unchanged) OCRs VobSub:
  its feature list covers "Import and OCR VobSub sub/idx binary
  subtitles", and its Matroska reader handles image-based subtitle
  tracks in MKV for command-line conversion (SE changelog: batch /
  cmd-line MKV support; the GUI's MKV "Import subtitle from Matroska"
  path lists image tracks and runs the same OCR engine). With an MKV
  that contains exactly one subtitle track there is no track-selection
  ambiguity on the CLI.

## 2. The chosen branch - extract to single-track MKV

**Extract VobSub to an intermediate .mkv, point SE at it. Two sentences of
code, no new tools.**

```
ffmpeg -y -hide_banner -nostdin -loglevel error \
    -i ripped.mkv -map 0:7 -c:s copy intermediate.mkv     # VobSub branch
SubtitleEdit /convert intermediate.mkv subrip /ocrengine:tesseract /ocrlanguage:en /outputfolder:...
```

vs. the existing PGS branch (unchanged):

```
ffmpeg ... -c copy intermediate.sup                        # PGS branch
SubtitleEdit /convert intermediate.sup subrip /ocrengine:tesseract ...
```

Rejected alternatives:

- **Extract to `.sub` directly with ffmpeg.** Impossible - no vobsub
  muxer exists (Section 1). Not a flag problem; the capability is
  absent.
- **Bundle/rely on mkvextract (MKVToolNix).** New external dependency,
  new CI bundle change, new `find_program` resolution path; violates
  the constraints for zero functional gain over the MKV-remux path.
- **Point SE at the original ripped MKV with a track selector.** SE
  5.2.0's CLI has no documented per-track subtitle selector for
  `/convert`; on a multi-track rip (movie MKVs routinely have 3-10
  subtitle streams) it would OCR the *first* image track, not the one
  the pipeline chose (and the whole point of stream 7 is that it is
  not always the first). The single-track intermediate is what makes
  "the one we chose" == "the one SE sees". Cost of the intermediate:
  one codec-copy remux of a subtitle stream only - megabytes, a
  fraction of a second.
- **OCR engine swap (e.g. vobsub2srt).** New dependency; SE already
  handles VobSub.

PGS behavior is untouched: same `.sup` filename, same extraction
command, same SE input. The only shared code is the filename decision.

## 3. Codec detection - where and what

`ProbedStream.codec_name` already carries the value from
`ffprobe -show_streams`: `"hdmv_pgs_subtitle"` on Blu-ray,
`"dvd_subtitle"` on DVD. pipeline.py already holds the chosen
`ProbedStream sub` when it calls `run_subtitle_ocr(job.input_path,
sub.index, video_out, workdir=rip_dir)`.

**Signature change (backward compatible):**

```python
def run_subtitle_ocr(
    mkv_path: str,
    stream_index: int,
    video_out_path: str,
    *,
    workdir: str,
    codec_name: str = "",                      # NEW; "" behaves as PGS
    se: SubtitleEditOcr | None = None,
    extract_binary: str = "ffmpeg",
    se_runner: Runner | None = None,
) -> OcrResult:
```

New module-level helper in subtitles.py (pure, headless-testable):

```python
def _intermediate_ext(codec_name: str) -> str:
    """Container extension for the extracted subtitle track.

    PGS (hdmv_pgs_subtitle) -> .sup, DVD VobSub (dvd_subtitle) -> .mkv
    (ffmpeg's only muxer that accepts dvd_subtitle copy; SE reads
    VobSub from MKV directly). Unknown subtitle codecs also get .mkv:
    MKV is the most permissive container, so it fails last, and the
    SubtitleEditOcr error names the input file for diagnosis.
    """
    return ".sup" if codec_name == "hdmv_pgs_subtitle" else ".mkv"
```

Why the `else -> .mkv` fallback rather than rejecting unknown codecs:
image-subtitle OCR only has two real families in our rips (PGS,
VobSub). A third codec through ffmpeg's MKV muxer will either work in
SE (win) or fail in SE with a clear "no SRT produced" error that names
the file (same fallback contract as today). A hard reject would turn a
possibly-working case into a guaranteed no-subtitles MP4.

pipeline.py change: pass the codec through one call site.

```python
ocr = run_subtitle_ocr(
    job.input_path, sub.index, video_out,
    workdir=rip_dir, codec_name=sub.codec_name,   # v0.2.16
)
```

That is the entirety of the pipeline.py diff. No UI change, no dry-run
change (OCR only runs in real runs), no `TitleJob` field change.

## 4. subtitles.py changes - exact

1. `run_subtitle_ocr` gains `codec_name: str = ""` (kw-only, default PGS
   to keep existing direct callers and tests source-compatible).
2. Replace the hard-coded `.sup` construction:

```python
ext = _intermediate_ext(codec_name)
img_path = os.path.join(
    workdir, os.path.splitext(os.path.basename(mkv_path))[0] + ext,
)
extract_subtitles(mkv_path, stream_index, img_path, binary=extract_binary)

srt_in = se.run(img_path, workdir, runner=se_runner)
```

   Every downstream reference to `sup_path` renames to `img_path`
   (three uses: extraction target, `se.run` input, final `os.remove`).
   The SRT output-name derivation inside `SubtitleEditOcr.run`
   (`splitext(basename(in_path))[0] + ".srt"`) is extension-agnostic -
   `movie.mkv -> movie.srt` works exactly like `movie.sup -> movie.srt`.

3. Extraction command: unchanged (`-map 0:N -c copy <out>`); ffmpeg
   picks the muxer from the extension. `.mkv` gets the matroska muxer
   with codec copy - valid for `dvd_subtitle`.

4. Error text: `extract_subtitles`'s existing message
   (`subtitle extraction failed: {stderr}`) needs no change - for
   unsupported codec/muxer combos stderr already says exactly what
   happened (that is how the original bug was diagnosed). One
   improvement: include the codec in the failure message from
   `run_subtitle_ocr`'s level is unnecessary; the pipeline warning
   already names the job. Keep messages as-is.

5. `OcrResult`, `SubtitleEditOcr`, `parse/normalize/write` stages: no
   changes. Zero-cue detection and the <50-cue note apply identically
   to DVD OCR output.

## 5. Fallback contract (unchanged)

pipeline.py catches `SubtitleOcrError` and records
`"{name}: subtitle OCR failed ({exc}); MP4 was produced without
subtitles."` - v0.2.16 is reached *through* that contract, not around
it. If SE 5.2.0's MKV/VobSub path misbehaves on a real disc (this
branch has never seen a real DVD VobSub yet - the 2026-10-02 run died
in ffmpeg before SE ever started), the failure surfaces as the same
warning class and the MP4 still ships. The stage line
`stage(f"OCR subtitles for {job.output_name} ...")` precedes it, so the
History view shows where it stopped.

subtitles.py: +6 lines (helper), ~4 lines changed (signature, filename
construction, renames). pipeline.py: 1 line. Tests: ~70 lines across two
files. Fits easily in one Forge session, and the PGS regression surface
is exactly one helper with a pinned unit test.
