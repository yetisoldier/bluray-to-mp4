# v0.2.33 — Frame-Exact Chunking for DVD AI Upscale

**Status:** design (approved direction; Eric sign-off pending implementation)
**Author:** Bob (architect)
**Implements:** chunking by frame index instead of time windows; gate on exact
frame counts instead of durations; pre-flight VFR refusal; retention of a
rejected mezzanine plus a written diagnostic.
**Fixes:** the 2026-10-17 Mamma Mia HWA six-GPU-hours-to-trash run (57 chunks
upscaled on the 3090 Ti, then the v0.2.31 duration gate tripped on this
disc's pinned ~15.05 s accumulated drift and fail-open encoded the original
720x480 rip. The gate worked; the upscale was discarded anyway).

**Why the gate trips on real discs:** `-ss/-t` seek/copy windows on an MKV
from a VOB-sourced MakeMKV rip do not land on exact frame boundaries, and
`duration_seconds` from the MakeMKV scan (`plan.duration_seconds`,
`pipeline.py:776`, title-derived) is an integer-second title duration, not
the container's stream extent. Frame counts per 120 s window jitter; at
23.976/29.97 the rounding error accumulates to ~15 s on a 113-minute disc.

## 2. v0.2.33 mechanism: cut and reassemble by **frame index**

### 2.1 Authoritative total frame count (one-time probe)

New helper in `bluray_to_mp4/ffprobe.py`:

```
probe_frame_count(path, *, binary="ffprobe") -> (total_frames: int, nb_frames_quoted: bool)
```

Implementation: two-pass probe, run once before any GPU work.

1. Fast pass: `ffprobe -v error -select_streams v:0
   -show_entries stream=nb_frames,nb_read_frames -of json`
   (no `-count_frames`; reads metadata only).
2. Slow pass: `ffprobe -v error -select_streams v:0 -count_frames
   -show_entries stream=nb_read_frames -of csv=p=0`
   (decodes every packet; ~20–60 s on a DVD rip, one-time, before any
   GPU hour is committed).

**Selection rule:** if slow-pass `nb_read_frames` > 0, it is authoritative.
If the slow pass fails/ffprobe errors, and the fast-pass `nb_frames` > 0,
use it but set a flag `frame_count_from_metadata=True` that is carried in
the plan and written into the diagnostic (§5). If both fail, raise
`UpscaleError("rip frame count could not be probed")` before any chunk
runs — honest refusal, ~30 seconds, no GPU time burned.

**Justification over alternatives:**
- `nb_frames` metadata *alone* is unreliable: MakeMKV writes it from
  container index and it can be absent or undercount on VOB-sourced DVD
  rips with open GOP / pulldown flagging. Documented known lie source.
- Packet count (`-show_entries format=nb_read_packets`-style without
  decode) counts packets, not frames; one packet can yield 0 or 2 frames
  after soft telecine, so it is also a lie source for DVDs.
- `-count_frames` performs an actual decode-count; it is the only ffprobe
  figure that cannot be wrong about *how many decoded frames the stream
  yields* — which is exactly the number our extraction must reproduce.
  Cost is one-time and small vs. 6 GPU-hours.

**Residual failure mode (stated honestly):** if the container has
duplicate/corrupt packets such that decoded-frame count under ffmpeg's
demuxer differs from what the decoder emits at extraction time, the total
could differ from the sum of extracted chunks. That is caught by the
per-chunk count assertion (§2.3) and the final gate (§4); the pipeline
fails open with the diagnostic. The failure mode is *detectable*, never
silent.

### 2.2 VFR pre-flight (the 6-hours → 30-seconds requirement)

New helper in `bluray_to_mp4/ffprobe.py`:

```
probe_cfr_check(path, *, binary="ffprobe") -> CfrVerdict
```

Runs in the same pre-flight as the frame count (piggyback on the
`-count_frames` call, which already decodes everything):

```
ffprobe -v error -select_streams v:0 -count_frames \
  -show_entries stream=r_frame_rate,avg_frame_rate,nb_read_frames \
  -of json <rip>
```

Verdict logic:

- Parse both rates with the existing `parse_frame_rate`
  (`ffprobe.py:97-110`). Let `r = value(r_frame_rate)`,
  `a = value(avg_frame_rate)`.
- If either is missing after parse: verdict `UNKNOWN` → treated as
  **refuse** for upscale (fail open with warning). A rip whose clock we
  cannot even name must not be rebuilt on a guessed constant clock.
- If `|r - a| / a > 0.001` (0.1%): verdict `VFR` → **refuse** pre-flight.
  Reassembling a genuinely variable-clock source at constant fps would
  re-create drift by construction; honest no in ~30 seconds.
- Else verdict `CFR`: proceed. This is the overwhelmingly common case —
  MakeMKV strips pulldown and emits CFR rips (23.976/1001, 29.97/1001) —
  and the Mamma Mia disc that tripped v0.2.31 lands here
  (r_frame_rate == avg_frame_rate within tolerance; its drift came from
  time-window chunking, not VFR).

Pipeline integration: immediately after `rip_fps = video_frame_rate(...)`
at `pipeline.py:760-767`, run `probe_cfr_check(job.input_path)`. On
`VFR`/`UNKNOWN`, append the refusal warning and set `video_input_path =
None` *without calling `run_dvd_upscale`* — this is the 30-second honest
no. The existing fail-open path (`pipeline.py:809-817`) already encodes
the original rip in that case; we reuse it by raising `UpscaleError`
pre-upscale and letting the same `try/except UpscaleError` catch it
(structurally: the pre-flight lives inside the `if job.upscale_mode !=
"off":` block, wrapped so its `UpscaleError` hits the same handler).

### 2.3 Frame-exact chunk plan

`UpscalePlan` gains:

```
total_frames: int | None = None        # from probe_frame_count; required at run time
chunk_frames: int | None = None        # derived: round(chunk_seconds * fps_float)
frame_count_from_metadata: bool = False
```

Chunk math (in `run_dvd_upscale`, replacing `upscale.py:357-359` and the
`-ss/-t` block at `upscale.py:373-375`):

```
fps_num, fps_den = parse plan.fps            # "30000/1001" -> 30000, 1001
fps_float = fps_num / fps_den
F = max(1, round(plan.chunk_seconds * fps_float))   # frames per full chunk
N = plan.total_frames
chunks = ceil(N / F)
for idx in range(chunks):
    first = idx * F
    count = min(F, N - first)                      # last chunk = remainder
```

Frame math is integer-exact: `first`/`count` are `int`s, never durations.
`chunk_seconds` remains a plan field so operators keep a ~2-minute mental
model; it is converted once via `round(120 * 24000/1001)` → 2877 frames
(113.99 s at that clock — irrelevant, since boundaries are indexed, not
timed). **Rounding choice:** `round()`, not `floor()`, so a nominal
"120 s" chunk at 23.976 is 2877 frames, closer to the human label.

### 2.4 Frame-exact extraction command shape

Verified against ffmpeg 8.0.1 on this host (`ffmpeg -h filter=select`
shows `expr`; `ffprobe -count_frames` supported). The extraction replaces
`-ss/-t` with a decode-filter approach:

```
ffmpeg -y -hide_banner -nostdin -i <rip.mkv> -an -sn \
  -vf "select='between(n,{first},{first+count-1})',<prepare_filter>" \
  -vsync 0 -start_number {first+1} in_dir/frame_%08d.png
```

Notes Forge must honor:

- `select=between(n,a,b)` addresses **decoded frame index** `n` (0-based)
  — this is the frame-exact anchor, independent of timestamps.
- `-vsync 0` (passthrough) is mandatory in the muxer path so ffmpeg does
  not duplicate/drop to hit an implied CFR output clock during PNG
  extraction; we want exactly the selected frames.
- Seeking is deliberately dropped (no `-ss`). DVD rips decode at >800 fps
  to PNG scale; a 113-minute disc is ~162 k decoded frames, but we decode
  the *prefix* per chunk which overlaps. Mitigation: use **output-seek
  with `select` consumed after a fast input seek to the nearest keyframe
  before `first`** — acceptable refinement: `-ss` expressed in seconds to
  ~1 keyframe early (container seek, cheap), then `select='gte(n, k)'`
  where `k` = `first - frames_before_keyframe`. Simpler first cut: no
  `-ss` at all; measure. If extraction becomes the bottleneck, Forge adds
  the hybrid seek as a non-breaking optimization (the frame indices are
  identical either way; timestamps are irrelevant).
- Keep the existing `_prepare_filter(plan.deinterlace)`
  (`upscale.py:246-252`) appended after `select` — unchanged.

Real-ESRGAN and mezzanine-segment steps (`upscale.py:414-475`) run
unchanged per chunk — `image2 -framerate plan.fps` is fine because a
segment is exactly `count` frames, so stamping at the verified-CFR clock
is, by construction, also timestamp-exact for that segment.

Per-chunk assertion inside the loop, immediately after extraction:

```
actual_in = _count_pngs(in_dir)
if actual_in != count:
    raise UpscaleError(
        f"chunk {idx+1}/{chunks} extracted {actual_in} frames; expected "
        f"{count} (frames {first}..{first+count-1})"
    )
```

And after Real-ESRGAN: `if _count_pngs(out_dir) != count: raise ...`.
Any mismatch → the outer `except Exception` at `upscale.py:524-533`
converts to `UpscaleError` → pipeline fail-open. No partial mezzanine can
escape.

### 2.5 Reassembly and total-count assertion

Concat (`upscale.py:491-514`) unchanged. After concat, before returning:

```
mezz_frames = probe_frame_count(str(output))  # slow pass on FFV1 mezzanine
if mezz_frames != plan.total_frames:
    raise UpscaleError(
        f"upscale mezzanine has {mezz_frames} frames; the rip has "
        f"{plan.total_frames}; refusing to encode a desynced upscale"
    )
```

`run_dvd_upscale` returns `(mezzanine_path, total_frames)` — signature
change is internal to the stage; pipeline call site updated accordingly.

Drift becomes zero by construction: segments contain exactly the rip's
frames, stamped at the rip's own verified CFR clock.

## 3. Gate rework — `verify_mezzanine_frames`

Replaces `verify_mezzanine_duration` (`upscale.py:293-334`; the function
is deleted; pipeline import at `pipeline.py:58-62` updated).

```
def verify_mezzanine_frames(
    mezzanine_path: str,
    rip_total_frames: int,
    *,
    probe_frames,          # injected probe_frame_count-shaped callable
) -> None:
    """v0.2.33 gate: mezzanine frame count must equal the rip's exactly."""
    if rip_total_frames <= 0:
        raise UpscaleError(
            "rip frame count unknown; refusing to encode a possibly "
            "desynced upscale"
        )
    try:
        mezz = int(probe_frames(mezzanine_path))
    except Exception as exc:
        raise UpscaleError(
            f"upscale mezzanine frame count could not be probed ({exc}); "
            "refusing to encode a possibly desynced upscale"
        ) from exc
    if mezz != rip_total_frames:
        raise UpscaleError(
            f"upscale mezzanine has {mezz} frames; the rip has "
            f"{rip_total_frames}; refusing to encode a desynced upscale"
        )
```

Semantics: **exact equality, no tolerance window.** Frame counts are
integers; any drift mechanism produces a nonzero integer difference. The
v0.2.31 duration tolerance (`0.5 s + 0.01%`) is retired with the gate.

Pipeline call site (`pipeline.py:800-808`) becomes:

```
verify_mezzanine_frames(
    video_input_path, rip_total_frames,
    probe_frames=probe_frame_count,
)
```

`rip_total_frames` is captured once at pre-flight (§2.1/§2.2) and reused;
no second decode of the rip. The mezzanine count is one extra
~30 s decode of an FFV1 MKV — acceptable.

The pinned v0.2.31 regression **flips**: the Mamma Mia drift shape
(mezzanine 15.05 s short) cannot occur under frame-exact reassembly; its
fixture is rewritten as a *pass* case pinning zero drift.

## 4. Retention on gate trip

Currently the failed path deletes: `upscale.py:524-533` unlinks a
partial `output` only inside `run_dvd_upscale`, but when
`verify_mezzanine_duration` raises *after* a successful return, the
mezzanine at `job.upscale_mezzanine_path` is left in the rip dir with no
diagnostic and is **overwritten** on retry (`upscale.py:366-368` unlinks
an existing output at the start of `run_dvd_upscale`).

v0.2.33 behavior, in the pipeline's `except UpscaleError` handler
(`pipeline.py:809-817`):

1. If `job.upscale_mezzanine_path` exists, rename it to
   `<name>_720p.rejected-<ISO8601>.mkv` alongside the original (rip dir,
   `.upscale/`). Never delete; operator decides.
2. Write `<name>_720p.rejected-<ISO8601>.diagnostic.json` containing:
   `rip_path`, `rip_total_frames`, `frame_count_from_metadata`,
   `rip_fps`, `r_frame_rate`, `avg_frame_rate`, `cfr_verdict`,
   `chunks`, `chunk_frames`, `expected_per_chunk` (list of ints),
   `mezzanine_frame_count` (if probeable), `error` (the UpscaleError text).
3. Warning text gains: "rejected mezzanine retained at <path>;
   diagnostic at <path>".

Drift becomes *measurable from artifacts*, not inferred from logs.

## 6. Version & changelog

`pyproject.toml:3` → `version = "0.2.33"`. CHANGELOG draft:

```
## [0.2.33] - 2026-10-18

### Fixed

- **DVD AI upscale now chunks by exact frame index, not time windows.**
  The rip's frame count is probed once (decode-counted, not metadata) and
  each chunk extracts frames [i*F, (i+1)*F) via ffmpeg's select filter.
  Accumulated duration drift — the failure that burned six GPU-hours on
  Mamma Mia HWA and still shipped the original rip — is impossible by
  construction.
- **The upscale gate now requires exact frame-count equality** between
  mezzanine and rip (was: duration within 0.5 s + 0.01%). A mismatch

  now retained next to a written diagnostic (expected vs actual counts,
  fps probe values) so future drift is measurable from artifacts.
- **Variable-frame-rate rips are refused before any GPU work.** A
  pre-flight check compares r_frame_rate vs avg_frame_rate; a true VFR
  rip fails open in seconds with an honest warning instead of after the
  upscale runs.
```

No UI changes beyond the new warning strings (fail-open message gains the
retained-mezzanine path; VFR refusal message added).

## 7. Risks / unverified items

1. **Extraction speed without `-ss`.** Full-decode `select` is correct but
   decodes the stream prefix per chunk. Real-ESRGAN at ~6 min/chunk
   dominates by an order of magnitude, so even 2× extraction cost is
   noise — but Forge must measure chunk-1 extraction time on the first
   real run and apply the hybrid keyframe-seek refinement (§2.4) if it
   exceeds ~10% of chunk time. Frame-index semantics are identical either
   way, so the optimization is safe to defer.
2. **`-count_frames` on the concatenated mezzanine** costs ~30 s extra
   per title. Accepted.
3. **Interlaced + yadif interaction:** deinterlace runs *after* `select`
   in the filter chain; yadif in default mode is 1 frame in → 1 frame
   out, frame counts preserved. `yadif=1` (double-rate) is not used
   anywhere in the codebase — verified by inspection of
   `_prepare_filter*` (`upscale.py:223-252`). OK.
4. **Could not verify on real hardware:** I did not run an actual Mamma
   Mia-scale extraction; the select-filter frame-index behavior is
   documented ffmpeg (verified present on host's ffmpeg 8.0.1) but the
   first real run should spot-check one chunk's `in_dir` count against
   `count` (which the new per-chunk assertion does automatically).
5. **`probe_frame_count` on exotic rips** (e.g. MKV with attached
   pictures as a second video stream): `-select_streams v:0` pins the
   first video stream, same one `video_frame_rate` reads. Consistent.
